# FTS5 tokenizer 對中文的實際 recall（2026-08-10）

Refs #2。決定 lexical 檢索用哪個 tokenizer 配置，並量測 `NLTokenizer` 的丟字行為。

探針：[`scripts/probe-tokenizer.swift`](../../scripts/probe-tokenizer.swift)。機器：MacBook Pro M5 Max，macOS 27.0，SQLite 3.54.0。
執行：`swiftc -O -o probe scripts/probe-tokenizer.swift && ./probe 2000 120 <seed>`。

> **本檔為 v4。** v1–v3 的數字皆已作廢——PR #8 的三輪 6-AI verify 各找出一批會系統性扭曲結果的量測缺陷。各版作廢原因列在最後。

## 方法

- **語料**：`~/.claude/projects/**/*.jsonl` 抽 2,000 個對話 text block（截斷 600 字元；每檔最多 4 個 block）。長度 median 253、min 20、max 600。
- **查詢集**：known-item retrieval，六 bucket，gold 是抽出該查詢的那份文件。CJK bucket 排除「整個 run」當查詢。
- **df 敏感度（配對設計）**：`df≤1` 與 `df≤5` **共用同一抽樣序列**（seed 不隨 cap 變），唯一差別是接受條件。
- **向量**：每個 track 固定單一 `NLContextualEmbedding` 模型，文件與查詢同模型，維度不合即中止。
- **指標**：Recall@20，機率 baseline 1.0%。
- **錯誤處理**：所有 `sqlite3_*` 與 embedding 失敗即中止；每個 tokenizer 跑 smoke test。

**隱私**：語料執行期直讀、只讀不寫；本檔與探針無任何語料片段。只有聚合數字進 repo。代價是需本機重跑才能重現——`CLAUDE.md` 隱私鐵律優先於可重現性的刻意取捨。

## 結果：報範圍，不報點估計

三個 seed（42 / 7 / 99），df≤1、Hant 向量軌：

| 配置 | 中文2字 | 中文3字 | 中文4字 | 英數 | 中英混雜 | 全體 |
|---|---|---|---|---|---|---|
| `unicode61`（預設） | 0% | 0% | 0% | 96–100% | 6–8% | **14–15%** |
| `trigram` | **0%** | 100% | 100% | 97–99% | 100% | **79–82%** |
| 斷詞 + `unicode61` | 31–35% | 30–37% | 44–52% | 97–100% | 11–19% | **39–43%** |
| `trigram` + 斷詞（OR / RRF 等價） | 31–35% | 100% | 100% | 97–100% | 100% | **86–88%** |
| vector-only [Hant] | 8–11% | 12–13% | 17–21% | 3–12% | 8–12% | **10–12%** |
| **lexRRF + vector [Hant]** | 39–42% | 100% | 100% | 96–99% | 100% | **87–89%** |

跨語彙同義桶 n 只有 3–4，三個 seed 分別是 0%／0%／33%——**樣本太小，不列入上表**，見下方缺口。

**而且它在兩輪都是 `df≤1`**（#10）：量測器對該桶硬性要求 gold 唯一，不遵守 `dfCap`。
這是刻意的——同義桶沒有 provenance（alias pair 是固定清單，gold 是「含另一側的那篇」），
`df>1` 時沒有有依據的 gold 可挑；而其他五桶的 gold 由「這個子字串從第 `i` 篇抽出」決定，
`df>1` 只是讓檢索變難。**所以下方 df 敏感度那張表的兩欄，對這個桶是同一組查詢。**

**seed 間變異約 ±1–2pp。** 早期版本引述單一 seed 的點估計（如「88%」）是過度精確；本檔一律報範圍。

**引用 86–88% 之前先看上一列**（#9）：`trigram` **單軌就已經是 79–82%**。中文三字、
中文四字、英數、中英混雜四個桶在 `trigram` 下已經接近或等於 100%——也就是說**大部分
查詢量從一開始就沒有懸念**，而斷詞帶來的增益幾乎全部集中在**中文雙字桶**
（0% → 31–35%）。

這不是說那個增益不重要——中文雙字是這份語料最常見的查詢形狀，`trigram` 在它上面是
**全滅**（0%），所以那一格正是整套組合存在的理由。但把 86–88% 當成「這套組合的貢獻」
會高估它：它主要衡量的是 `trigram` 本來就會做對的部分。

## 決定

**lexical 採 `trigram` + 斷詞雙欄位；OR 與 RRF 在三個 seed 上完全等價，取 RRF**（與向量路合成方式一致）。

**`unicode61` 單獨使用排除**（14–15%）。

**加入向量融合**：86–88% → 87–89%。**增益在三個 seed 都是 +1pp**——方向一致、幅度小，且**全部來自中文雙字桶**（31–35% → 39–42%，約 +7pp）。向量模型固定用 Hant（全體 10–12%，全面優於 Latn 的 5–6%，含英數桶）。

### df 敏感度：唯一性要求未灌水（配對設計）

同一抽樣序列、只放寬接受條件：

| 配置 | df≤1 | df≤5 |
|---|---|---|
| trigram + 斷詞（RRF） | 86% | **87%** |
| lexRRF + vector | 87% | **88%** |
| 斷詞 + `unicode61` | 39% | **48%** |

`df≤5` 樣本的實際 df 分布：`df=1` 384、`df=2` 92、`df=3` 56、`df=4` 41、`df=5` 27。

**這是全體分布，沒有分桶，而 per-bucket 的數字當時沒有被記下來**（#9）。所以
**無法判斷放寬 df 之後各桶的難度是否等比例改變**——中文雙字桶可能吸收了多數的
`df≥2` 樣本，也可能相反，這份紀錄回答不了。

量測腳本（`scripts/probe-tokenizer.swift`）還在，所以原則上重跑就能補；但那需要同一份
2,000 篇的語料抽樣與同一組 seed，屬於**重跑量測**而不是補文件。**在補之前，上表的
df 敏感度只能讀成全體層級的結論。**

放寬後不降反微升。「`df==1` 系統性挑出稀有字串因而灌水 lexical」**不成立**。

誠實邊界：`df≤5` 仍在挑相對罕見的字串。真正常見的子字串在 top-20 / 2000 的設定下 gold 語意本就不明，超出 known-item 設計能回答的範圍。

### 兩個未解決的缺口

1. **中文雙字查詢**：最佳 39–42%。`trigram` 的 3 字元硬底線讓它掛零，斷詞路補到 31–35%，向量再補約 7pp。沒有配置解決它。
2. **跨語彙同義**：n=3–4，三個 seed 為 0%／0%／33%。**樣本太小不能下任何結論**，只能說沒有觀察到任何配置穩定處理「查 ANN 命中近似搜尋」。這是 #7 的理由。

## `NLTokenizer` 丟字

| 斷詞方式 | 平均丟字率 | 最大 | >5% 的文件 |
|---|---|---|---|
| naive（整份直接斷詞） | 0.40% | 54.8% | 39 / 2000 |
| **by-script（先切 CJK/Latin 段再斷詞）** | **0.00%** | **0.0%** | **0 / 2000** |

丟字率＝字元多重集合差集（輸入有、token 沒有的字元數 ÷ 輸入字元數）。

**決定：ingest 端先依 script 切段，只對 CJK 段呼叫 `NLTokenizer`。**

### 這個度量能證明什麼、不能證明什麼

**能證明**：by-script 不丟字元。**不能證明**：by-script 切得有用。一個「把每個字都切成
單字」的斷詞同樣會拿 0.00% 丟字率，卻毫無檢索價值——**丟字率是必要條件，不是充分條件**。

**而那個 0.00% 有一半是建構性的，不是量出來的**（#9）。`Sources/LTMIndex/Segmentation.swift`
對非 CJK 段的處理是：

```swift
// 非 CJK 段照原樣帶過去：它自己的空白就是詞界。
let trimmed = run.text.trimmingCharacters(in: .whitespacesAndNewlines)
if !trimmed.isEmpty { output.append(trimmed) }
```

**非 CJK 段根本不呼叫 `NLTokenizer`。** 對那一半文字，「零丟字」不是量測結果，是
**定義上不可能非零**——沒有東西在斷它，就沒有東西會掉。

所以這張表真正量到的是：**`NLTokenizer` 在 CJK 段上不丟字**。那仍然是有價值的結論
（naive 那一列證明它在混合文字上會丟，最大 54.8%），但它的涵蓋範圍比「by-script 不丟
字元」這句話讀起來窄。

「有用」由 recall 表獨立證明：斷詞路在中文各桶拿到 31–52%，而未斷詞的 `unicode61` 是 0%。兩個指標各證一半，缺一不可。

### 丟字成因：不宣稱知道

控制網格（naive 平均丟字率 / 該格 n）：

| 長度＼Latin run | 0–1 | 1–5 | 5–20 | 20+ |
|---|---|---|---|---|
| 0–60 | 0.0% / n=6 | 3.9% / n=93 | 0.3% / n=208 | — |
| 60–150 | 0.0% / n=1 | 3.6% / n=7 | 0.3% / n=396 | 0.0% / n=107 |
| 150–400 | — | — | 0.9% / n=10 | 0.5% / n=243 |
| 400+ | — | — | — | 0.1% / n=929 |

**這份資料不足以支撐任何機制解釋。** 丟字率偏高的格子 n 只有 7–93，兩軸高度共線（長文本幾乎必然有多個 Latin run），n 從 1 到 929 極不均。

本檔先後出現過三個機制假說，全部撤回：

| 版本 | 主張 | 撤回原因 |
|---|---|---|
| 診斷 #2 | 語言偵測被 Latin 帶偏，run 越多越易丟 | 網格顯示相反方向 |
| v1 | 不是混雜，是短文本 | 單軸解釋與網格不符 |
| v2 | 長度與 run 數的交互作用 | 支撐該說法的格子 n=7 |

**現在的立場**：naive 在 39/2000 份文件丟字、最大丟掉 54.8%；by-script 在全部 2000 份零丟字。**修法有效，成因未知，不再猜測。** 要回答成因需專門的控制實驗（固定長度掃 run 數、固定 run 數掃長度），超出 #2 範圍。

## 版本差異

| 項目 | v1 | v2 | v3 | v4 |
|---|---|---|---|---|
| `unicode61` | 40% | 17% | 17% | **14–15%** |
| `trigram` | 66% | 80% | 80% | **79–82%** |
| trigram+斷詞 | 82% | 86% | 87% | **86–88%** |
| vector-only | 8%（打平） | 16% | 19% | **10–12%** |
| fused | 56%（低於單路） | 88% | 89% | **87–89%** |

- **v1 作廢**：查詢未去重且允許整個 CJK run 當查詢（高估 `unicode61`）、`embed()` 無條件 `.traditionalChinese`、「fused」漏掉 trigram 路（導致方向相反的「融合不是免費的」結論）、所有錯誤被吞掉。
- **v2 作廢**：**兩個獨立的變更同時發生，而先前這一行只寫了其中一個**（#9）。
  - **向量側**：`pickScript()` 依文字內容路由 embedder，使查詢與 gold 文件可能落在不同
    模型的向量空間；維度不合時靜默截斷。
  - **lexical 側**：v3 把 `gold` 的定義從「第一個含該子字串的文件」改成「**抽出該查詢的
    來源文件 `i`**」。那是獨立的語意變更，與向量無關。
  - **為什麼必須分開歸因**：v2→v3 的 lexical 數字也動了（`unicode61` 17%→14–15%、
    斷詞路 43%→39–43%），而**向量修復不可能影響純 lexical 的召回**。把全部變動歸給
    向量修復，會讓讀者以為 lexical 那條線是穩定的。
- **v3 作廢**：df 敏感度用了帶 `dfCap` 的 seed，兩組是**獨立樣本**而非配對——差異無法歸因於 cap 本身。
- **v4**：配對 df 設計、三 seed 變異範圍、丟字度量的能力邊界說明。

## 重議觸發

換 tokenizer 配置 = 重建全部 lexical 索引、本檔數字作廢。需重測：SQLite 版本變更、macOS 更新（`NLTokenizer` 或 `NLContextualEmbedding` revision）、語料中文比例大幅變動、#7（查詢擴展）實作後、#1 的評估 harness 就緒後（屆時應以真實查詢與 negative case 重測；本檔的 known-item 數字只作**配置間的相對比較**）。
