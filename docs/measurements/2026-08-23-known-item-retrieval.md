# known-item 檢索品質——三軌的第一份分報（2026-08-23）

Refs #33（change `wire-evaluation-machinery`）。這是 `RecallNDCG` 與 `ChannelBreakdown`
這兩個評分基元的**第一個呼叫端**產出的第一份紀錄——它們先前實作完成、測試齊全、
沒有任何東西呼叫它們。

- 量測器：[`scripts/measure-retrieval-quality.swift`](../../scripts/measure-retrieval-quality.swift)（`swift run measure-retrieval`）
- 產生器：[`Sources/LTMEval/KnownItemHarness.swift`](../../Sources/LTMEval/KnownItemHarness.swift)
- 語料抽樣：[`scripts/sample-corpus-scales.py`](../../scripts/sample-corpus-scales.py)

## 這份紀錄**不涵蓋**什麼——先講，因為它最容易被誤讀

1. **它量的是檢索，不是記憶策略。** 本檔一個數字都不能拿來推論
   `archival`／`human-like`／`conservative` 之間的優劣。策略比較要的是使用歷史與
   交錯呈現，與本檔的機制完全無關（見 `wire-evaluation-machinery` 的 design：
   兩條評估路徑要的東西相反）。CLAUDE.md 的「策略比較目前沒有任何量測支撐」
   在這份紀錄之後**仍然成立**。
2. **查詢是從它們要檢索的那一段裡抽出來的，所以不代表真實查詢。** 使用者不會把
   一段內文的 2–4 個字原封不動貼進搜尋框。這種查詢的性質——極短、無語境、逐字取自
   目標——會系統性地偏袒逐字比對的通道而懲罰語意通道，下面 vector 那一欄就是這個
   效應的直接後果。
3. **母體排除了事件日誌看不見的檢索失敗。** 這是 `strategy-comparison` spec 既有的
   結構性限制（不留 query 原文 ⇒ 沒有真實查詢可以重放），本檔繼承它：這裡的「查詢」
   全部由產生器造出，因此本檔量不到「使用者查了卻沒找到、於是放棄」那一類事件。
4. **`mixed` 桶結構上抽不到。** 產生器只回兩種東西：一段連續漢字的內部子字串
   （→ 三個 cjk 桶），或一個 ASCII 英數詞（→ `latin-alnum`）。**它不可能產出同時含
   漢字與英數的查詢**，所以 `mixed` 那一列在下表裡不是「觀測到 0」，是「這個產生器
   到不了」。要涵蓋它得先改產生器。

## 方法

- **語料**：`~/.claude/projects/` 的 1,600 檔抽樣（`sample-corpus-scales.py`，seed 42），
  建成獨立索引 18,470 chunk。**不對生產索引量測**——量測器對兩個根都要求顯式指定，
  少任何一個都會退回預設值而不報錯（與 `measure-rrf-ties.swift` 同一條守衛，#18 verify R1）。
- **抽樣**：seeded SplitMix64 shuffle 取前 N。同一組 `(語料, 樣本數, seed)` 給出逐字
  相同的輸出——實測 seed 42 跑兩次，`diff` 為空。
- **查詢導出**：優先取連續漢字段的**內部**子字串（長度 2–4），否則取一個 ≥4 字元的
  ASCII 英數詞。「內部」是必要的——拿整段當查詢會讓 gold 幾乎必然排第一，量到的是
  「完全比對能不能命中」而不是檢索品質。導不出來的樣本跳過並計數。
- **三軌**：`lexical` = trigram + segment 兩條 FTS 通道的 RRF；`vector` = 向量通道；
  `fused` = 三條全開（生產路徑）。三軌都走
  `RetrievalEngine.search(query:limit:scope:channels:)`——**量測器裡沒有任何檢索邏輯**，
  在那裡重算一份 RRF 會量到那份重算的行為（「兩個寫者＝兩份會漂移的規格」）。
- **指標**：Recall@20 → nDCG@10 的兩階段函式（`scoreRecallAndRanking`）。nDCG 只在
  被 recall 到的那些對上平均——沒 recall 到就沒有排序品質數字，這是 `RecallNDCGOutcome`
  的型別層事實。
- **隱私**：查詢與 gold 指標只活在評估過程中，`KnownItemReport` 的每個欄位都是計數或
  比率（`KnownItemHarnessTests` 對序列化後的 bytes 下了斷言）。本檔只有聚合。
- 機器：MacBook Pro M5 Max、macOS 27.0、embedding revision
  `12784592-5D67-4F4C-83D6-A346519146AE#1`。

## 讀得出來的三件事

**（一）三軌報告確實會分岔，而且分岔的方向在表上讀得出來。** 這正是三軌形狀存在的
理由：`cjk-2char` 的 vector 欄在兩個 seed 上都是 0.0%（沒有任何一對被 recall 到，
所以 nDCG 欄是 `—` 而不是 0），而同一桶的 lexical 是二成多。只看整體的 48.5% 會把
這個結構完全洗掉。

**（二）vector 這一軌在這種查詢下幾乎全滅（整體 2.4% / 2.0%），而那多半是查詢的
性質、不是通道的性質。** 這裡要非常小心不要過度推論：本檔的查詢是 2–4 個字的逐字
片段，`NLContextualEmbedding` 對這種無語境碎片產出的向量，與整段 chunk 的向量本來
就不該接近。**這份紀錄無法分辨**「向量通道對真實查詢也這麼弱」與「向量通道只是不
適合這種抽出來的碎片查詢」——要分辨得有真實查詢，而那正是不留 query 原文所排除的
東西。任何引用本檔數字去說「向量通道沒用」的說法都超出它的涵蓋範圍。

**（三）`fused` 沒有比 `lexical` 好，甚至略低。** 兩個 seed 都是這個方向
（49.5→48.5、49.4→46.7）。機制上說得通：RRF 把一條幾乎全是雜訊的通道也算進分數，
它貢獻的排名會把真正的 gold 擠出前 20。**但這份紀錄不能據此改任何配置**——差距落在
個位數百分點、n≈490、兩個 seed 的差距本身就相差三倍（1.0pp vs 2.7pp），這是抽樣
變異量級。它是一個**值得追下去的訊號**，不是一個結論；而要把它變成結論，需要的正是
第 2 點說的真實查詢。

## 這份紀錄能支撐什麼引用

- 「三軌分報會分岔，`cjk-2char` 的向量軌在抽出來的短查詢上是零」——可以，指名本檔。
- 「檢索評估的機具已就緒並跑過真實語料」——可以。
- 「向量通道對真實查詢的效果」——**不行**，本檔量不到真實查詢。
- 「fused 應該關掉向量通道」——**不行**，見上面第三點。
- 任何策略之間的比較——**不行**，本檔與策略無關。
