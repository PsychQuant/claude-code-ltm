# known-item 檢索品質——三軌的第一份分報（2026-08-23）

Refs #33（change `wire-evaluation-machinery`）。這是 `RecallNDCG` 與 `ChannelBreakdown`
這兩個評分基元的**第一個呼叫端**產出的第一份紀錄——它們先前實作完成、測試齊全、
沒有任何東西呼叫它們。

- 量測器：[`scripts/measure-retrieval/main.swift`](../../scripts/measure-retrieval/main.swift)（`swift run measure-retrieval`）
- 產生器：[`Sources/LTMEval/KnownItemHarness.swift`](../../Sources/LTMEval/KnownItemHarness.swift)
- 語料抽樣：[`scripts/sample-corpus-scales.py`](../../scripts/sample-corpus-scales.py)

## 這份紀錄**不涵蓋**什麼——先講，因為它最容易被誤讀

1. **它量的是檢索，不是記憶策略。** 本檔一個數字都不能拿來推論
   `archival`／`human-like`／`conservative` 之間的優劣。策略比較要的是使用歷史與
   交錯呈現，與本檔的機制完全無關（見 `wire-evaluation-machinery` 的 design：
   兩條評估路徑要的東西相反）。CLAUDE.md 的「策略比較目前沒有任何量測支撐」
   在這份紀錄之後**仍然成立**。
2. **查詢是從它們要檢索的那一段裡抽出來的，所以不代表真實查詢。** 使用者不會把
   一段內文的 2–4 個字原封不動貼進搜尋框。這種查詢是極短、無語境、逐字取自目標的
   片段——而**本檔量不到這個形式對各通道的影響有多大**。下面第（二）點會說明為什麼
   那是一個這份量測設計上分辨不了的問題，而不是一個可以順帶下的結論。
3. **母體排除了事件日誌看不見的檢索失敗。** 這是 `strategy-comparison` spec 既有的
   結構性限制（不留 query 原文 ⇒ 沒有真實查詢可以重放），本檔繼承它：這裡的「查詢」
   全部由產生器造出，因此本檔量不到「使用者查了卻沒找到、於是放棄」那一類事件。
4. **`mixed` 桶結構上抽不到。** 產生器只回兩種東西：一段連續漢字的內部子字串
   （→ 三個 cjk 桶），或一個 ASCII 英數詞（→ `latin-alnum`）。**它不可能產出同時含
   漢字與英數的查詢**，所以 `mixed` 那一列在下表裡不是「觀測到 0」，是「這個產生器
   到不了」。要涵蓋它得先改產生器。

## 方法

- **語料**：`~/.claude/projects/` 的 1,600 檔抽樣（`sample-corpus-scales.py`，seed 42），
  建成獨立索引 18,470 chunk。**不對生產索引量測**——量測器對兩個根都要求顯式指定，
  少任何一個都會退回預設值而不報錯（與 `measure-rrf-ties.swift` 同一條守衛，#18 verify R1）。
- **抽樣**：seeded SplitMix64 shuffle 取前 N。同一組 `(語料, 樣本數, seed)` 給出逐字
  相同的輸出——實測 seed 42 跑兩次，`diff` 為空。

  > **這份紀錄的數字產生於 harness 加上淺檢索計數之前**（`5381587`，2026-08-24，
  > 本紀錄完成的次日）。那個計數要抓的正是本紀錄可能含有的東西：某一軌回傳的名次
  > 少於判定視窗時，「清單太短」與「真的沒命中」在 `scoreRecallAndRanking` 裡產生
  > 同一個 `.notRecalled`，於是 recall 被低估。
  >
  > **本紀錄裡有多少對受此影響，沒有量過**——要知道就得用新版 harness 重跑，而重跑
  > 需要重建那份 1,600 檔的抽樣索引。所以：本紀錄的 recall 數字應讀成**下界**，
  > 而不是點估計。表中幾格 `n` 很小（4、7、10、12）的 vector-nDCG 尤其要當心。
  >
  > 上面的可重現性宣稱（「跑兩次 diff 為空」）也只在當時的 harness 上驗過。新版
  > 多了一個計數欄位，輸出形狀因此不同——那條宣稱**沒有**在新版上重驗。
- **查詢導出**：優先取連續漢字段的**內部**子字串（長度 2–4），否則取一個 ≥4 字元的
  ASCII 英數詞；**若那個詞逐字等於整段文字就放棄這個樣本**。「不得等於整段」是必要
  的——拿整段當查詢會讓 gold 幾乎必然排第一，量到的是「完全比對能不能命中」而不是
  檢索品質。導不出來的樣本跳過並計數。

  （這條在 ASCII 那側**初版漏了**：一段內容剛好只有一個詞時會回傳整段。#33 的
  verify 抓到，已修並補上會紅的回歸測試；本檔的數字是修正後重跑的。）
- **三軌**：`lexical` = trigram + segment 兩條 FTS 通道的 RRF；`vector` = 向量通道；
  `fused` = 三條全開（生產路徑）。三軌都走
  `RetrievalEngine.search(query:limit:scope:channels:)`——**量測器裡沒有任何檢索邏輯**，
  在那裡重算一份 RRF 會量到那份重算的行為（「兩個寫者＝兩份會漂移的規格」）。
- **指標**：Recall@20 → nDCG@10 的兩階段函式（`scoreRecallAndRanking`）。nDCG 只在
  被 recall 到的那些對上平均——沒 recall 到就沒有排序品質數字，這是 `RecallNDCGOutcome`
  的型別層事實。
- **隱私**：查詢與 gold 指標只活在評估過程中，`KnownItemReport` 的每個欄位都是計數或
  比率（`KnownItemHarnessTests` 對序列化後的 bytes 下了斷言）。本檔只有聚合。
- 機器：MacBook Pro M5 Max、macOS 27.0、embedding revision
  `12784592-5D67-4F4C-83D6-A346519146AE#1`。

### 兩件關於這張表怎麼讀的事

**nDCG 的 `n` 就是那一格能承載多少推論。** vector 那一欄兩個 seed 的 `n` 是 12 與
10。十來個觀測的三位小數不是一個可以拿來比較的數字，本檔也不拿它比較。

**`meanNDCGAmongRecalled` 把「recall 到但落在第 10–20 名」的硬 0 混進平均。**
兩階段函式的定義是：gold 在前 20 名內就算 recalled，但 nDCG 的視窗只有前 10，
所以落在 11–20 名的對回報 `.recalled(ndcgAt10: 0)`。那些 0 進了這個平均。所以
「被 recall 到的那些對的平均排序品質」這句話要理解成**含視窗外的零**，而不是
「平均排在第幾名」。

## 讀得出來的三件事

**（一）三軌分報確實會分岔，而分岔在表上讀得出來。** 這正是三軌形狀存在的理由：
`cjk-2char` 的 vector 欄在兩個 seed 上都是 0.0%（`n=0`，所以 nDCG 是 `—` 而不是 0），
而同一桶的 lexical 是二成多。只看整體的 48.5% 會把這個結構完全洗掉。

**（二）vector 這一軌在這種查詢下幾乎全滅（整體 2.4% / 2.0%）。**

這是觀測。**本檔不對它做歸因**——初稿在這裡寫了「那多半是查詢的性質、不是通道的
性質」，而同一段的下一句就說「這份紀錄無法分辨」兩者。兩句直接牴觸，前者已刪。

能說的是有兩個競爭解釋，而這份量測**設計上就分辨不了它們**：

- 查詢是 2–4 個字的逐字片段，`NLContextualEmbedding` 對這種無語境碎片產出的向量，
  與整段 chunk 的向量本來就不該接近；
- 向量通道對真實查詢也這麼弱。

要分辨得有真實查詢，而那正是不留 query 原文所排除的東西。**任何引用本檔數字去說
「向量通道沒用」的說法都超出它的涵蓋範圍**，而說「這只是查詢形式的問題」同樣超出。

**（三）`fused` 沒有比 `lexical` 好，而赤字幾乎全部集中在 `cjk-2char`。**

初稿只報了整體（49.5→48.5、49.4→46.7）並據此談機制。那犯了第（一）點自己警告的
錯——整體數字會洗掉集中。逐桶看：

| 桶 | seed 42（lexical → fused） | seed 43（lexical → fused） |
|---|---|---|
| cjk-2char | 24.8% → 20.4%（−4.4pp）| 25.2% → 17.9%（−7.3pp）|
| cjk-3char | 91.6% → 89.7%（−1.9pp）| 89.6% → 87.5%（−2.1pp）|
| cjk-4plus | 91.7% → 91.7%（0.0pp）| 96.6% → 94.8%（−1.8pp）|
| latin-alnum | 33.7% → 35.2%（**+1.5pp**）| 33.7% → 34.2%（**+0.5pp**）|

方向在兩個 seed 上一致：中文桶被拉低、拉得最多的是 `cjk-2char`，而 `latin-alnum`
反而略升。機制上說得通——RRF 把 vector 貢獻的排名也算進分數，那條通道在中文桶
recall 是 0.0%／1.9%／6.2%，它推上來的候選會把 gold 擠出前 20。

**但這份紀錄不能據此改任何配置。** 它量的是**這種抽出來的碎片查詢**，而第（二）點
已經說明這種查詢對向量通道系統性不利。真實查詢下 vector 貢獻什麼，本檔量不到。
這是一個**值得追下去的訊號**，不是一個結論。

### 這個產生器的一個性質，會影響上面的讀法

兩條導出路徑產生的查詢**性質不同**：中文取的是連續漢字段的**真子字串**（一定不是
完整的詞），拉丁取的是一個**完整的詞**。所以 `latin-alnum` 那一列（約四成樣本）在
「查詢與 gold 的字面重疊」這個維度上與三個中文桶不可比，而它們被合進了粗體的
「全部」列。**跨桶比較請看分桶，不要看合併列。**

## 這份紀錄能支撐什麼引用

- 「三軌分報會分岔，`cjk-2char` 的向量軌在抽出來的短查詢上是零」——可以，指名本檔。
- 「檢索評估的機具已就緒並跑過真實語料」——可以。
- 「fused 相對 lexical 的赤字集中在 `cjk-2char`，方向在兩個 seed 上一致」——可以，
  但必須連同第（三）點的但書一起引用。
- 「向量通道對真實查詢的效果」——**不行**，本檔量不到真實查詢。
- 「向量通道之所以差只是因為查詢形式」——**不行**，同樣是本檔分辨不了的歸因。
- 「fused 應該關掉向量通道」——**不行**，見第（三）點。
- 任何策略之間的比較——**不行**，本檔與策略無關。
