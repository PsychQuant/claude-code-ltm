# RRF 平手發生率——`conservative` 到底有沒有作用面（2026-08-22）

Refs #18（源自 #1 verify R3，requirements lens）。**本檔在 #18 的 verify R1 之後大幅
改寫**：初版的量測方法有一個會**製造假平手**的缺陷，而初版從觀測推出的「結構上限」
與「全語料外推有界」兩條結論已撤回。過程記在最後一節，因為它是這份紀錄怎麼讀的一部分。

## 為什麼要量這個

`conservative` 在 base score 兩兩相異時**可證明等同於 `archival`**（回傳原順序、
位移全 0——測試 `conservativeNeverReordersCandidatesWithDifferentBaseScores` 就是
在證這件事）。所以**平手發生率就是這一檔的全部價值**：若平手幾乎不發生，這一檔
在實務上是佔位符；若常發生，它是一個真的策略。

**結論：不是佔位符。作用面高度集中在 `cjk-2char`，其餘四桶都很低。**

## 方法

- **量的是生產路徑，不是一份重寫**。探針不含任何檢索邏輯；它呼叫
  `ltm query --json --k 20 --all-projects`（預設 `archival`，即檢索原順序）並讀回
  真正的 `score` 與 `band`。在探針裡重算一次 RRF，量到的會是那份重寫的平手率
  （CLAUDE.md：「同一件事有兩個寫者，就是兩份會漂移的規格」）。
- **分數用原始 JSON token 字串比對，不解析成 `Double`**。理由見下方「方法的一個
  缺陷」——這是初版與本版最實質的差別。
- **分桶用生產環境的 `QueryClassifier`**（探針編譯時直接帶入
  `Sources/LTMEval/QueryClass.swift`），不抄一份分類規則。
- **查詢集 104 條**，全部自行撰寫的通用技術詞彙（CLAUDE.md 隱私邊界：不從
  `~/.claude/projects/` 抄任何片段）。分桶不在查詢檔內宣告，由分類器在執行期算。
- **兩個判準分開報**：「僅 score」是 issue #18 原文的判準；「band+score」是
  `ConservativeStrategy` **實際**用的判準（band-major 排序讓帶界上可能出現「分數
  相同但不同帶」的相鄰對，那種對策略不作用）。
- **長度 1 的平手段不計**——一個候選的區段裡沒有東西可以互換（#18 明寫）。
- 機器：MacBook Pro M5 Max、macOS 27.0、embedding revision
  `12784592-5D67-4F4C-83D6-A346519146AE#1`。

### 方法的一個缺陷，以及它怎麼修的

初版用 `JSONSerialization` 把 `score` 解析成 `Double` 再比相等，並附了一個實驗宣稱
「JSON 的 Double 是忠實的」。那個實驗測的是**寫入端**：`1.0/65.0` 印成
`0.015384615384615385`、`(1.0/65.0).nextUp` 印成 `…387`，兩串不同，所以序列化單射。

**但需要的性質在讀取端，而那一端不成立。** 同一組值實測：

```
引擎值 1.0/65.0                          bits = …648
引擎值 (1.0/65.0).nextUp                 bits = …649
JSONSerialization("0.015384615384615385") bits = …650   ← 兩者
JSONSerialization("0.015384615384615387") bits = …650   ← 合併
stdlib Double("0.015384615384615385")     bits = …648   ← 正確捨入
```

`JSONSerialization` 的數字解析不是正確捨入的（對 `1/65` 差 2 ulp），而且把那對
1-ulp 鄰居併成同一個值。影響方向只有一邊：引擎內相等的值必印成同一串、讀回同一個值
（**漏不掉真平手**），但相異的值可能讀成相同值（**會製造假平手**）。範圍：

| 分數空間 | 引擎內互異值 | 經 `JSONSerialization` 往返後 |
|---|---:|---:|
| 單通道 `1/(60+r)`，r ∈ [1,100] | 100 | 100（無碰撞）|
| 兩通道 `1/(60+a)+1/(60+b)` | 5,009 | **5,004**（5 組合併）|

**現行做法**：從原始 JSON 位元組取出 `"score"` 的 token 字串直接比對，完全不經解析器。
寫入端單射保證「token 相同 ⟺ 引擎 `Double` 相同」。`band` 仍走 `JSONSerialization`
——它是整數，不受浮點解析影響。

這條修法有回歸鎖：`scripts/rrf-tie-fixtures/ulp-neighbours` 餵的正是上面那對值，
期望輸出是「不平手」。把實作改回解析 `Double`，它會變成 100% 平手——**驗過會紅，
而且為對的理由紅**。

### 規模階梯（不是單點）

語料規模會改變答案，所以量三個規模，讓「規模會不會改變結論」變成被量到的東西。
三個語料由 `scripts/sample-corpus-scales.py` 產生：`random.seed(42)` 對全語料
`shuffle` 一次後**取前綴**（不是 `random.sample`——後者在 k=1600 會換演算法而破壞
巢狀性），所以 100 ⊂ 400 ⊂ 1600 檔，腳本結束前當場自證巢狀性。

### 段長：不是恆為 2，而且不隨規模單調

初版報告「所有平手段長度都是 2，沒有例外」，並據此推出一個上限。**那是抽樣假象。**
修正後的量測在 400 檔那一階出現 **2 段長度 3**（`latin-alnum`），而 1600 檔那一階
又回到全部長度 2。段長既不封頂於 2、也不隨規模單調。

理由是可構造的：平手**不限於**單通道候選。`rrfK = 60`、通道深度 `max(20×5, 50) = 100`
時，兩通道候選的分數是 `1/(60+a) + 1/(60+b)`，而這個式子在該值域內會碰撞——

```
1/(60+36) + 1/(60+100) = 1/96  + 1/160 = 1/60
1/(60+40) + 1/(60+90)  = 1/100 + 1/150 = 1/60
1/(60+60) + 1/(60+60)  = 1/120 + 1/120 = 1/60
```

三組 rank 完全不同、band 相同、分數是**同一個有理數**（不是浮點巧合）。所以長度 3
以上的區段可以完全不需要 `trigram` 貢獻獨佔候選。

## 機制：`cjk-2char` 的集中來自 `trigram` 的 3 字元硬底線

由 `scripts/rrf-tie-mechanism.sh` 產生（在 400 檔那一階的索引上跑）：

| 查詢 | trigram 命中 | 單通道組 | 相鄰平手 |
|---|---:|---|---:|
| `測試` | 0 | `segment`×9、`vector`×8 | 8 |
| `索引` | 0 | `segment`×10、`vector`×10 | 10 |
| `記憶` | 0 | `segment`×10、`vector`×10 | 10 |
| `快取` | 0 | `segment`×10、`vector`×10 | 10 |
| `型別` | 0 | `segment`×10、`vector`×10 | 10 |
| `相容性` | 8 | `vector`×12 | 0 |
| `一致性` | 20 | （無） | 0 |
| `資料庫` | 20 | （無） | 1 |

2 字 CJK 查詢的 `trigram` 通道**整條空掉**——那正是
[`2026-08-10-fts5-tokenizer.md`](2026-08-10-fts5-tokenizer.md) 記錄的「`trigram` 的
3 字元硬底線讓它掛零」。於是 `segment` 與 `vector` 各自貢獻一組互斥的單通道候選，
名次一對一對撞，`segment@r` 與 `vector@r` 同分。3 字以上時 `trigram` 開始命中並與
`segment` 成對（成為 2 通道候選、換一個帶），單通道組只剩一組，組內名次互不相同。

同一個結構事實既壓低了中文雙字的召回（#2 量到最佳 39–42%），也**製造了**
`conservative` 主要的作用面。

**但這個機制不是平手的唯一來源**，表格自己就有反例：`資料庫` 的 trigram 命中 20、
**沒有任何單通道組，卻仍有 1 個相鄰平手**。那是兩通道候選之間的分數碰撞（上一節的
有理數恆等式）。所以「單通道對撞」解釋的是 `cjk-2char` 的**集中**，不是平手的全部。

## 判讀

**`conservative` 不是佔位符，但它的作用面高度集中。**

- 在 `cjk-2char` 上它幾乎總是有事可做：1600 檔那一階，該桶 **99.6% 的候選**落在
  平手段內、100% 的查詢至少有一段。
- 其餘四桶都在個位數以下；`mixed` 在三個規模上都是 0.0%。

「整體 13.5%」這個數字會把這種集中洗掉——這正是 #2 要求分桶報告的理由。

### 對 #17 的意義

#17 恢復 `conservative` 時的論證是「『僅作 tie-breaker』在這套詞彙裡可以表達」，
而它是否**值得存在**被明寫成待量測。本量測回答了那一半：**在這個查詢集與這些語料
子集上，它有實際作用面，而且集中在 #2 判定為最重要的那個桶。**

它**沒有**回答「`conservative` 比 `human-like` 或 `archival` 好」——那需要
`(查詢, 應命中的 turn)` 的評估集（#16）。本量測不涉及命中品質，只量「有沒有可動的空間」。

## 這份量測不涵蓋什麼

- **不涵蓋排序品質。**「有平手可打破」與「打破得對」是兩件事。
- **不涵蓋全語料規模。** 三階都是真實語料的巢狀子集，最大的一階（1,600 檔）仍遠小於
  全部（量測當日 8,780 檔）。全量索引跑了約 4.5 小時未完成，為了讓階梯跑完而中止。
  **全語料是未觀測的**，而且**沒有任何一格可以宣稱有界**——初版曾對 `cjk-2char` 宣稱
  有界，那條推論已撤回（見上方「段長」一節）。
- **查詢集是人工撰寫的便利樣本**，不是真實查詢的隨機抽樣。桶內只有 20–24 條，桶內
  百分比的精度有限。`cjk-2char` 與其餘桶的差距大到不像抽樣噪音，但確切數值不該被
  當成點估計。
- **不涵蓋 `displacementBound` 的正確值。** 觀測到的段長多為 2，但 400 檔那一階已經
  出現長度 3，所以「bound = 1 夠用」在本語料上都不成立於全部情形。
- **不涵蓋浮點脆弱性的未來。** #18 記錄的脆弱處仍成立：目前的融合是純除法加法
  （`RetrievalEngine.search` 的 `1.0 / (Self.rrfK + Double(rank + 1))` 累加，不含
  正規化步驟），所以精確相等站得住；上游改成先正規化再相加時，這一檔會**安靜地**
  退化成 `archival`，而本檔的所有數字會一起變成 0 且不報錯。

## 這份紀錄改寫過一次，過程留著

初版（commit `e6494ef`）在 #18 的 verify R1 拿到 6 條 HIGH，其中四條打在本檔上：

1. **「52.6% 是結構上限」是無效推論。** 我從「觀測到段長恆為 2」推出「20 個候選最多
   配成 10 對 → 10/19」。而「成對」本身是從「只有兩條通道貢獻單通道候選」推來的
   **觀測**，不是結構保證。修正後的量測直接證偽它：400 檔那一階出現長度 3 的段。
2. **「JSON 的 Double 是忠實的」被它自己的例子證偽**（見「方法的一個缺陷」）。
3. **「`cjk-4plus` 與 `mixed` 裡逐字等同 `archival`」是無條件斷言**，證據只有各 20 條
   查詢的零觀測。修正後 `cjk-4plus` 在兩個較大的規模上都是 0.3%，不是 0。
4. **「巢狀子集」無法查證**——抽樣腳本沒提交。devil's advocate 只能猜，它猜了
   `random.sample` 並據此證明不巢狀；我實際用的是 `shuffle`+前綴，那確實巢狀。
   **但它的實質成立**：未提交的方法不可查證，而那次誤判本身就是證明。更糟的是，
   寫可提交版本時發現初版另有一個真缺陷——目的地路徑用 `f.parent.name / f.name`，
   不同 project 下的同名檔互相覆蓋（400 檔只落地 398 個、1600 檔只落地 1584 個），
   而**被覆蓋的是哪幾個隨複製順序而定**，在不同規模不必相同。所以初版的檔案層
   巢狀性確實破了。

還有一條與本檔的敘事有關：初版的 CHANGELOG 與本檔都寫著「`ConservativeStrategy`
的 doc comment 一度宣稱這一檔『實務上會命中』，已撤回」。**git 歷史說相反**：

**修法都改成性質而非列舉**：doc comment、README、spec 三處不再複述任何數字（連
「某桶是 0」都不複述），只留定性結論與指向本檔的指標；spec 的條文改成「不得從
**任何**被觀測到的段長分佈推導上限」。抽樣腳本則**不再接受目的地參數**——它用
`tempfile.mkdtemp()` 自己建立並印出來，沒有外來路徑就沒有要判定的東西（另留一道
inode 身分的 sanity check 當縱深，五條旁路實測全擋）。

**留著這兩節的理由**：這份紀錄的每一個數字都經過兩次「看起來對、其實有洞」的迭代，

- **R1 的形狀**：我做了一個實驗、得到想要的答案就停手，而那個實驗測的不是我需要的
  那個性質（測寫入端單射，需要的是讀取端保真）。

  「這個弱化後的版本現在還對嗎」——而它剛好落在被新資料打掉的那一格。
