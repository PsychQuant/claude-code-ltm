# RRF 平手發生率——`conservative` 到底有沒有作用面（2026-08-22）

Refs #18（源自 #1 verify R3，requirements lens）。
探針：[`scripts/measure-rrf-ties.swift`](../../scripts/measure-rrf-ties.swift)、
查詢集：[`scripts/rrf-tie-queries.txt`](../../scripts/rrf-tie-queries.txt)。

## 為什麼要量這個

`conservative` 在 base score 兩兩相異時**可證明等同於 `archival`**（回傳原順序、
位移全 0——測試 `conservativeNeverReordersCandidatesWithDifferentBaseScores` 就是
在證這件事）。所以**平手發生率就是這一檔的全部價值**：若平手幾乎不發生，這一檔
在實務上是佔位符；若常發生，它是一個真的策略。

那個發生率先前**沒有量過**，而 `ConservativeStrategy` 的 doc comment 一度寫著
「平手很常見，所以這個判準在實務上會命中」——沒有量測支撐的宣稱，已撤回。

**結論先講：發生率不低，但它幾乎完全是一個 `cjk-2char` 現象。** 依據在下方。

## 方法

- **量的是生產路徑，不是一份重寫**。探針不含任何檢索邏輯，它呼叫
  `ltm query --json --k 20 --all-projects`（預設 `archival`，即檢索原順序）並讀回
  真正的 `score` 與 `band`。在探針裡重算一次 RRF，量到的會是那份重寫的平手率
  （CLAUDE.md：「同一件事有兩個寫者，就是兩份會漂移的規格」）。
- **JSON 的 Double 是忠實的**。已實測 Foundation 的序列化在 1 ulp 粒度上單射：
  `1.0/65.0` → `0.015384615384615385`、`(1.0/65.0).nextUp` → `0.015384615384615387`；
  相等的值印出相同字串。所以讀回來的 Double 與引擎內部位元相同，精確相等比較成立。
- **分桶用生產環境的 `QueryClassifier`**（探針編譯時直接帶入
  `Sources/LTMEval/QueryClass.swift`），不抄一份分類規則。
- **查詢集 104 條**，全部是自行撰寫的通用技術詞彙（CLAUDE.md 隱私邊界：不從
  `~/.claude/projects/` 抄任何片段）。分桶不在查詢檔內宣告，由分類器在執行期算。
- **兩個判準分開報**：
  - 「僅 score」= issue #18 原文的判準（相鄰兩筆分數相等）
  - 「band+score」= `ConservativeStrategy` **實際**用的判準。band-major 排序讓帶界上
    可能出現「分數相同但不同帶」的相鄰對，那種對策略不作用；只看 score 會高估。
- **長度 1 的平手段不計**——一個候選的區段裡沒有東西可以互換（#18 明寫）。
- 機器：MacBook Pro M5 Max、macOS 27.0、embedding revision
  `12784592-5D67-4F4C-83D6-A346519146AE#1`。

### 規模階梯（不是單點）

語料規模會改變答案：候選要「只命中單一通道」才容易對撞，而通道深度固定
（`max(k*5, 50)` = 100），語料越大、長尾越長、單通道命中越多。所以量三個規模，
讓「規模會不會改變結論」變成被量到的東西而不是假設。三個語料是**巢狀**的
（小的是大的子集，`random.seed(42)` 抽自真實語料），所以規模是唯一變動的因素。

### `cjk-2char` 在最大的一階已經**觸頂**，不是還在爬

k=20 而平手成對出現，所以該桶的極限是「20 個候選全部配成 10 對」：相鄰配對 19 對
中有 10 對同分＝**10/19 = 52.6%**，候選覆蓋 100%。大語料量到的正是這兩個數
（52.6% / 100.0%），逐字等於上限。

這件事對外推很重要：`cjk-2char` 的平手率**不可能**在更大的語料上超過 52.6%，
所以全語料未觀測這個缺口，對這個桶而言是**有界的**——它已經在天花板上。
其餘四桶仍在低檔，方向不明，那部分的外推沒有這個保證。


**兩個判準在三個規模上完全相同**（「僅 score」＝「band+score」）：本語料上沒有出現
「分數相同但跨帶」的相鄰對。所以 issue #18 原文那個較寬的判準，在這裡沒有高估——
但那是**觀測結果，不是保證**，兩欄仍分開報。

**所有平手段長度都是 2，沒有例外。**

### 機制：這是 `trigram` 3 字元硬底線的下游後果

平手要發生，需要**兩個不同通道各自貢獻一組「只命中該通道」的候選**，且它們在
各自通道內的名次對撞（RRF 分數是 `Σ 1/(k + rank_i)`，單通道候選的分數就是
`1/(k + rank)`，名次相同即分數相同）。逐查詢檢查證實了這一點：

| 查詢 | trigram 命中 | 單通道組 | 相鄰平手 |
|---|---:|---|---:|
| `測試` | 0 | `vector`×8、`segment`×8 | 8 |
| `索引` | 0 | `vector`×10、`segment`×10 | 10 |
| `記憶` | 0 | `vector`×10、`segment`×10 | 10 |
| `快取` | 0 | `vector`×10、`segment`×10 | 10 |
| `型別` | 0 | `vector`×10、`segment`×10 | 10 |
| `相容性` | 7 | `vector`×13 | 0 |
| `一致性` | 20 | （無） | 1 |
| `資料庫` | 20 | （無） | 1 |

（n=400 的索引上量的。）2 字 CJK 查詢的 `trigram` 通道**整條空掉**——那正是
[`2026-08-10-fts5-tokenizer.md`](2026-08-10-fts5-tokenizer.md) 記錄的
「`trigram` 的 3 字元硬底線讓它掛零」。於是只剩 `segment` 與 `vector` 兩條通道，
各自貢獻一組互斥的單通道候選，名次一對一對撞，`segment@r` 與 `vector@r` 同分。

**這解釋了段長恆為 2**：兩條通道 → 平手成對出現。三條通道同時只出這種候選才會
出現長度 3，而那需要 `trigram` 也貢獻獨佔候選，與它掛零互斥。

3 字以上時 `trigram` 開始命中並與 `segment` 成對（成為 2 通道候選、換一個帶），
單通道組只剩 `vector` 一組，組內名次互不相同 → 分數互不相同 → 平手消失。

同一個結構事實既壓低了中文雙字的召回（#2 量到最佳 39–42%），也**製造了**
`conservative` 唯一的作用面。這不是巧合，是同一條硬底線的兩面。

## 判讀

**`conservative` 不是佔位符，但它的作用面極度集中。**

- 在 `cjk-2char` 上它幾乎總是有事可做，而且能動到的是**列表裡幾乎每一個候選**
  ——每組平手都是一對，`displacementBound = 1` 恰好容許把該對對調。
- 在 `cjk-3char` / `latin-alnum` 上它偶爾作用；在 `cjk-4plus` 與 `mixed` 上，
  本量測**一次都沒有觀測到**平手，也就是這兩桶裡 `conservative` 逐字等同 `archival`。

「整體 X%」這個數字會把這種集中洗掉——這正是 #2 要求分桶報告的理由，而它在這裡
再次成立。

### 對 #17 的意義

#17 恢復 `conservative` 時的論證是「『僅作 tie-breaker』在這套詞彙裡可以表達」，
而它是否**值得存在**被明寫成待量測。本量測回答了那一半：**在這個語料與這個
查詢集上，它有實際作用面，而且集中在 #2 判定為最重要的那個桶。**

它**沒有**回答「`conservative` 比 `human-like` 或 `archival` 好」——那需要
`(查詢, 應命中的 turn)` 的評估集（#16），本量測不涉及命中品質，只量「有沒有
可動的空間」。

## 這份量測不涵蓋什麼

- **不涵蓋排序品質。** 「有平手可打破」與「打破得對」是兩件事。前者是本檔，
  後者需要 ground truth。
- **不涵蓋全語料規模。** 三個規模都是真實語料的巢狀子集，最大的一階（1,584 檔）
  仍遠小於全部（8,754 檔）。全量索引跑了約 4.5 小時仍未完成，為了讓階梯跑完而
  中止——所以全語料是**未觀測**的。`cjk-2char` 那一格例外：它已經觸及結構上限
  52.6%，更大的語料不可能更高，這一格的外推是有界的。其餘四桶沒有這個保證。
- **查詢集是人工撰寫的便利樣本**，不是真實查詢的隨機抽樣。桶內只有 20–24 條，
  所以桶內百分比的精度有限。`cjk-2char` 與其餘桶的差距大到不像抽樣噪音，但
  桶內的確切數值不該被當成點估計。
- **不涵蓋 `displacementBound` 的正確值。** 段長恆為 2 這件事讓 `bound = 1` 在
  本語料上剛好足夠（一對能完全對調），但那是觀測不是論證——換一個 tokenizer
  配置就可能出現更長的段。
- **不涵蓋浮點脆弱性的未來。** #18 記錄的那個脆弱處仍然成立：目前的融合是純
  除法加法、不含會累積誤差的正規化，所以精確相等站得住；上游改成先正規化再相加
  時，這一檔會**安靜地**退化成 `archival`，而本檔的所有數字會一起變成 0 且不報錯。

## 重現

```bash
swift build -c release

# 探針必須與生產的 QueryClass.swift 一起編——分類規則只有一份
swiftc -O -o /tmp/rrfties scripts/measure-rrf-ties.swift Sources/LTMEval/QueryClass.swift

# 兩個根必須成對設定；只設一個時探針會拒跑並說明理由
LTM_CORPUS_ROOT=<語料> LTM_DERIVED_ROOT=<索引> \
  /tmp/rrfties .build/release/ltm scripts/rrf-tie-queries.txt 20
```

規模階梯的語料是 `random.seed(42)` 從 `~/.claude/projects/` 抽出的巢狀子集
（100 / 400 / 1600 檔，複製到暫存目錄；語料本身唯讀，未被寫入）。同名檔案在
複製時會覆蓋，所以實際檔數是 100 / 398 / 1,584。

### 探針本身驗過會動

「不可能失敗的量測比沒有量測更糟」（CLAUDE.md）。平手偵測器餵過一組手算過答案的
固定輸入（6 筆、刻意在帶界放一組「同分但不同帶」的相鄰對），八個輸出欄位全部與
手算相符：相鄰平手 4/5 = 80.0%（僅 score）對 3/5 = 60.0%（band+score）、
有段查詢 100%、段數 2、段長 2 與 3、覆蓋 5/6 = 83.3%、最長段 3。
**那組 80% vs 60% 的差距同時證明了兩個判準真的被分別計算**，不是同一個數字印兩次。
