# `ltm build` 的峰值記憶體對語料規模（#46）

**日期**：2026-08-26
**binary**：`.build/release/ltm`（分批提交之後，commit `414fc73`）
**方法**：合成語料三個尺寸，`/usr/bin/time -l` 取 maximum resident set size
**腳本**：[`scripts/measure-build-memory.sh`](../../scripts/measure-build-memory.sh)

## 為什麼用合成語料而不是真實語料

真實語料只給得出**一個點**（而且要等數十分鐘）。三個點才看得出線性與否，而
「它是不是線性」正是 `#46` 要回答的問題——沒有它，任何上限值都是猜的。

代價寫明：合成 chunk 的長度分布與真實語料不同，所以**絕對值不可外推到真實語料**
（見下方的反證）。

## 結果

| turns | chunks | 峰值 RSS | wall |
|---|---|---|---|
| 200 | 200 | 118 MB | 4.3 s |
| 800 | 800 | 203 MB | 15.2 s |
| 3,200 | 3,200 | 543 MB | 64.6 s |

**在量測範圍內是線性的**，而且兩段斜率一致：

- 200 → 800（+600 chunk）：+85 MB → **0.142 MB/chunk**
- 800 → 3,200（+2,400 chunk）：+340 MB → **0.142 MB/chunk**

擬合：`RSS ≈ 90 MB + 0.142 MB × chunks`（**僅在 200–3,200 這個範圍內**）。

## 這個結果推翻了 #46 的前提

`#46` 假設記憶體風險來自向量累積（`newVectors`）。**分批提交（#44）之後那一項
已被壓到上限**：`batchChunkTarget = 2,000` × 512 維 × 4 B ≈ **4 MB**，而且不隨語料
成長。

但 RSS 仍然隨 chunk 數線性成長。所以成長的**不是向量**。

查證後的實際來源：`CorpusScanner.scan()` 一次回傳 `chunks: [CorpusChunk]`，
每個 chunk 帶**完整文字**（`CorpusScanner.swift:44` 的 `public let text: String`），
而 `IndexBuilder.build()` 從頭到尾持有它，外加 `grouped` 的第二份 struct 陣列
（文字因 COW 共用，struct 陣列不共用）。

**掃描結果才是無上限累積的那一項，而 `#44` 的分批完全沒有碰到它。**

## 為什麼不能外推到真實語料

同一天的真實觀察：9,851 個 `.jsonl`／5.6 GB 的語料，build 峰值 RSS 約 **2.3 GB**。

若套用上面的擬合，2.3 GB 反推出約 **16,000 chunk**——而 `2026-08-08-baseline.md`
估真實語料是 **280,000 chunk** 量級。差了一個數量級以上。

**所以這條線在真實語料上不成立**，而這正是「不可外推」的實證，不是推測：合成
chunk 明顯比真實 chunk 大很多（每個 chunk 攤到 142 KB，遠超過文字本身），per-file
與 per-chunk 的固定開銷在兩種語料上的比例不同。

要得到真實語料的那條線，得在真實語料上取多個點——例如限定 project 數量逐步放大。
**那份量測還沒有做。**

## 這份紀錄支持與不支持的結論

**支持**：
- 峰值 RSS 隨 chunk 數成長，且**在受控條件下是線性的**。
- 成長來自掃描結果而非向量——後者已由 `#44` 的分批封頂。

**不支持**：
- 任何「N 個 chunk 會用掉 M GB」對真實語料的預測。
- 任何具體的預設上限值。要挑它，需要真實語料上的多點量測。

## 導出的決定

`#46` 要的「加上限」不能加在向量那一側——那裡已經有界了。真正需要的是**讓
scanner 串流**（分批吐 chunk 而不是一次全給），而那是比 `#44` 更大的介面改動，
應該有自己的診斷與決定。

在那之前可做的是**具名拒絕**：估算值超過預算時停下來說清楚，而不是讓 OS 決定。
估算的依據就是這份紀錄，而它的限度也在這份紀錄裡。
