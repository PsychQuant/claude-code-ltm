# `ltm build` 的峰值記憶體對語料規模（#46）

**日期**：2026-08-26
**binary**：`.build/release/ltm`（分批提交之後，commit `414fc73`）
**方法**：合成語料三個尺寸，`/usr/bin/time -l` 取 maximum resident set size
**腳本**：[`scripts/measure-build-memory.sh`](../../scripts/measure-build-memory.sh)

> **2026-08-26 修訂（跨模型盲驗之後）。** 本檔第一版宣稱「這個結果推翻了 #46 的
> 前提」並指名了一個**未經隔離量測**的因果來源。六個獨立 reviewer 中的四個各自
> 推翻了那兩件事。修訂內容與理由記在最後一節「這份紀錄先前說錯了什麼」——
> **保留而不是刪除**，因為 v0.3.0 的 release notes 引用過舊結論。

## 為什麼用合成語料而不是真實語料

真實語料只給得出**一個點**（而且要等數十分鐘）。三個點才看得出線性與否，而
「它是不是線性」正是 `#46` 要回答的問題——沒有它，任何上限值都是猜的。

代價寫明：合成 chunk 的長度分布與真實語料不同，所以**絕對值不可外推到真實語料**。

## 結果

| turns | chunks | 峰值 RSS | wall |
|---|---|---|---|
| 200 | 200 | 118 MB | 4.3 s |
| 800 | 800 | 203 MB | 15.2 s |
| 3,200 | 3,200 | 543 MB | 64.6 s |

**在量測範圍內是線性的**，而且兩段斜率一致：

- 200 → 800（+600 chunk）：+85 MB → **0.142 MB/chunk**
- 800 → 3,200（+2,400 chunk）：+340 MB → **0.142 MB/chunk**

擬合：`RSS ≈ 90 MB + 0.142 MB × chunks`（**僅在 200–3,200 這個範圍內**）。

## 這個結果**沒有**推翻 #46 的前提

第一版寫的是「推翻了」。那是錯的，四條理由各自獨立成立：

**(a) #46 逐字預先駁回過這條論證。** 第一版的核心論證是「分批之後向量那一側
已經有界，所以上限不能加在那裡」。而 #46 的 Problem 段寫著：

> **但分批不等於有界限**：批次大小是開發者挑的常數，而「這個常數在多大的語料上
> 會用掉多少記憶體」仍然沒有人回答。修完 #44 之後這個問題還在，只是變小。

第一版提出的正是被這段排除掉的論證，而且沒有引用、沒有反駁它。

**(b) 那個前提本身是假的。** 第一版寫「`batchChunkTarget = 2,000` × 512 維 × 4 B
≈ 4 MB，而且不隨語料成長」。實際上批次以**整個來源**為單位組裝，上界是
比 `batchChunkTarget` 大、且隨最大來源成長（公式的唯一一份在
`IndexBuilder.batchChunkUpperBound(target:largestSource:)`；本檔刻意不複述——先前
複述的那個版本是錯的）。使用者自己
語料裡最大的 session 檔有 4,322 個可索引 chunk，該檔整個進同一批 ≈ 8.8 MB，
加上 `VectorSidecar.encode` 同時存活的 `Data` ≈ 18 MB。詳見 [#47](https://github.com/PsychQuant/claude-code-ltm/issues/47)。

查法：

```bash
BIG=$(ls -S ~/.claude/projects/**/*.jsonl | head -1)
grep -c '"type":"text"' "$BIG"        # 可索引 chunk 的下界
```

**(c) 「前提」被偷換了。** #46 缺的三項是 (1) 沒有上限 (2) 沒有量測 (3) 沒有
OOM 以外的失敗方式；`newVectors` 只是**舉例**的變數名。這份量測處理的是第 (2) 項。
而它自己的數據——RSS 隨 chunk 數線性成長——**恰恰是第 (1) 項仍然成立的證據**，
只是無界的那一項換了個名字。把 1/3 的進度寫成「推翻了前提」，在 CHANGELOG 與
release notes 上讀起來就是結案。

**(d) 折衷版也沒做。** 第一版自己在「導出的決定」寫「在那之前可做的是具名拒絕」
——那是提案不是實作。

## 成長來源：只有相關性，沒有查證過的因果

RSS 隨 chunk 數線性成長。**成長的不是向量**（向量在這個合成語料上每 chunk 2 KB，
三個尺寸合計都在雜訊以下）。除此之外，**這份實驗定位不出因果來源**。

第一版寫「查證後的實際來源：`CorpusScanner.scan()` 一次回傳帶完整文字的 chunk」。
那句話**被它自己的數字否證**：

| | |
|---|---|
| 合成 chunk 的文字大小 | **630 bytes**（`'第 k 段內容。' + '測試語料需要足夠長度才能切成 chunk。' × 12`，UTF-8）|
| 800 → 3,200 增加的**文字**總量 | **1.5 MB** |
| 同區間觀察到的 **RSS** 增量 | **340 MB** |
| 差距 | **約 225 倍** |

即使算進 JSON 解析中間物、Swift `String`／struct 陣列的 overhead 與 COW 第二份
struct 陣列，都填不上兩個數量級。擬合出的 142 KB/chunk 遠大於 chunk 文字本身，
**所以「持有完整文字」不是現有數字支撐得起的解釋**。

查法（任何人可重跑）：

```bash
python3 -c "t='第 7 段內容。'+'測試語料需要足夠長度才能切成 chunk。'*12; print(len(t.encode()))"
# → 630
```

**尚未排除的其他來源**（實驗對它們沒有解析度，因為三個尺寸同時改變 turns、
chunks 與檔案數，且**沒有對照組**）：

- on-device embedding provider 的 native allocation（不計入 Swift heap，但計入 RSS）
- SQLite / FTS5 的 segment 與 page cache
- autorelease pool 在長迴圈內未排空
- scanner 的 JSON 解析中間物（與「持有完整文字」是不同的機制）

**能區分它們的後續量測**（各自只動一個變數）：

| 條件 | 排除的機制 |
|---|---|
| scan-only（不 embed、不寫 DB）| scanner 自身 vs 下游 |
| scan 後立即釋放，再 embed | 「持有」vs「產生」|
| 固定 scanner 結果，重複 embed | embedding 的 native allocation |
| 停用向量寫入 | 側車與 `encode` 的 `Data` |
| 停用 DB insert | SQLite / FTS |
| **固定 chunk 數、改變文字長度** | 文字大小是不是自變數 |
| **固定文字總量、改變檔案數** | per-file 固定開銷 |

最後兩列是關鍵：第一版的因果宣稱若成立，倒數第二列必須有強相關。**那一列還沒跑。**

## 為什麼不能外推到真實語料

同一天的真實觀察：9,851 個 `.jsonl`／5.6 GB 的語料，build 峰值 RSS 約 **2.3 GB**。

**這個點的比較基礎有兩個限制，第一版沒有標**：

1. **它是分批提交之前的觀察**（#46 記錄的時間點在 `414fc73` 之前），而表格三個點
   都在之後。兩者不是同一個 binary，不可直接排在同一條線上。
2. 真實語料的 chunk 數**沒有量過**，只有 `2026-08-08-baseline.md` 的 280,000 量級
   估計，而那個估計早於現行 chunker（`CorpusScanner` 現在是一 turn 一 chunk）。

所以第一版那段「反推 16,000 chunk vs 估計 280,000，差了一個數量級以上」是**用一個
自稱只有數量級精度的推估**去支撐一個數量級的結論——循環且不成立，已移除。

第一版另寫「合成 chunk 明顯比真實 chunk 大很多（每個 chunk 攤到 142 KB）」。
**方向很可能相反**：合成 chunk 是 630 B，真實對話 turn 通常更長。而括號裡的證據
把 **RSS 斜率**當成了 **chunk 大小**——那正是上一節指出的錯誤。

要得到真實語料的那條線，得在真實語料上取多個點——例如限定 project 數量逐步放大。
**那份量測還沒有做。**

## 這份紀錄支持與不支持的結論

**支持**：

- 峰值 RSS 隨 chunk 數成長，且**在受控合成條件下、200–3,200 這個範圍內是線性的**。
- 成長的不是向量（在此合成語料上向量項在雜訊以下）。

**不支持**：

- 任何「N 個 chunk 會用掉 M GB」對真實語料的預測。
- 任何具體的預設上限值。
- **任何關於成長來源的因果宣稱**——包含第一版指名的 scanner。
- 「向量那一側已經有界」——見 (b) 與 #47。
