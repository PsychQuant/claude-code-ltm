# tool payload 佔語料的比重（#6）

**日期**：2026-08-26
**機器**：MacBook Pro M5 Max
**語料**：本機 `~/.claude/projects` 取樣 300 個 `.jsonl` 檔

## 為什麼量這個

`#6` 主張「tool 索引只存 metadata、不存 payload」會切斷決策證據——很多觀點改變由
test failure、benchmark 數字、compiler error 觸發，而那些只活在 tool 輸出裡。

在決定要不要改索引策略之前，先量兩件事：**丟掉的是多少**，以及**現在看得見的是
多少**。本 repo 的紀律是沒有量測就不得宣稱，而「資料量大」這個常見的反對理由本身
就是一個沒量過的宣稱。

## 量了什麼

對取樣的 `.jsonl`，逐行解析 `type` 為 `user` / `assistant` 的 turn，統計
`message.content` 底下各種 block 的**數量**與**字元量**。字元量的計法：

- `text` → `text` 欄位長度
- `tool_use` → `input` 的 JSON 序列化長度
- `tool_result` → `content`（字串直接算，否則 JSON 序列化）
- `thinking` → `thinking` 欄位長度
- content 是純字串的 turn → 字串長度

## 結果

**turn 數 29,949，其中含 `text` block 而會被索引的：5,522（18.4%）。**

| block 種類 | 數量 |
|---|---|
| `tool_result` | 9,448 |
| `tool_use` | 9,441 |
| `thinking` | 5,556 |
| `text` | 4,473 |
| （content 是純字串） | 1,057 |
| `image` | 17 |

| 字元量（總 61,335,448） | | |
|---|---|---|
| `tool_result` | 40,318,745 | **65.7%** |

## 結論

**現行索引看得見的是 21.3% 的字元量，看不見 78.7%。**

`CorpusScanner.indexableText` 只取 `type == "text"` 的 block，其餘（`tool_use`、
`tool_result`、`thinking`、`image`）整個丟棄。所以現況比 `#6` 描述的更徹底：
**不是「tool 索引只存 metadata」，是根本沒有 tool 索引**——連工具名與成敗都沒存。

`thinking` 的 0 字元值得單獨說：那 5,556 個 block 的 `thinking` 欄位在取樣中都是
空字串（內容以 `signature` 形式存在，不是明文）。所以它不在「丟掉了可讀證據」的
討論範圍內。

## 這份紀錄**不**涵蓋的

- **那 78.7% 裡有多少是有檢索價值的。** `tool_result` 包含大量重複的檔案內容、
  目錄列表、建置輸出。體積大不等於證據多，而反過來也不成立。要回答這個問題需要
  一組 `(查詢, 應命中的 turn)` 的評估集，而那還不存在（#33）。
- **索引它的成本。** 沒有量索引時間、資料庫大小、或向量數量的增幅。
- **隱私面。** `tool_result` 會包含檔案內容與命令輸出，其中可能有第三方逐字內容
  ——那是本 repo 的隱私邊界直接管的東西。這份紀錄只說有多少，不說該不該。

## 給決定用的一句話

**丟掉的不是邊角，是大部分。** 但「大部分」本身不構成索引它的理由，正如「資料量
大」不構成不索引的理由——兩邊都需要上面那三項還沒量的東西。
