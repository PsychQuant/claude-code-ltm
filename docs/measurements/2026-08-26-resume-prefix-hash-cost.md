# 續讀前綴雜湊的成本（#5）

**日期**：2026-08-26
**機器**：MacBook Pro M5 Max（18 核、128 GB）
**語料**：本機 `~/.claude/projects`，當下狀態

## 為什麼量這個

`#5` 指出 `prefixHash` 有一個兩難：

- 只涵蓋固定開頭 → 檔案中段被改而 size 未變時，誤判為可續讀。
- 涵蓋全部 `processedBytes` → 每次啟動都要重讀所有已處理的位元組，隨語料成長退化。

**第一角已經關掉了**：現行實作雜湊的是 `readBytes(handle, from: 0, count: processed)`
——整段已處理前綴，不是固定開頭。所以剩下的問題只有第二角，而它是一個**效能**問題。

本 repo 的紀律是沒有量測支撐的效能宣稱一律不得出現，所以在決定要不要換成分塊
Merkle hash 之前，先量它現在多貴。

## 量了什麼

`~/.claude/projects` 底下**每一個** `.jsonl` 檔，從頭讀到尾並算 SHA-256。這是續讀
檢查的**上界**：實際的續讀只雜湊 `processedBytes`（≤ 檔案大小），而且只對狀態裡
還有紀錄的檔案做。

**不涵蓋**：解析、分塊、向量、寫入。這份紀錄只回答「重讀＋雜湊本身有多貴」。

## 結果

| | |
|---|---|
| `.jsonl` 檔數 | 9,565 |
| 總位元組 | 5,433,795,308（5.43 GB）|
| 全部讀 + SHA-256 | **3.96 秒** |
| 吞吐 | 1,373 MB/s |

量測腳本（可重跑）：走訪 `~/.claude/projects`、對每個 `.jsonl` 以 1 MiB 為單位
讀入並 `hashlib.sha256().update()`，計時涵蓋讀與雜湊。

## 結論

**現在不換 Merkle。** 在當下語料規模，這條路徑的上界是約 4 秒，而它換到的東西
（中段改寫必然被偵測到）已經由「雜湊整段前綴」這個做法提供了。

分塊 Merkle 買的是**成本隨改動量而非總量成長**，代價是一份新的樹狀狀態要維護、
要處理塊邊界與檔案截斷，而那些都是新的出錯面。

## 重議觸發

以下任一成立就該重新量、重新決定：

1. 語料超過約 **20 GB**（線性外推約 15 秒；那個量級下「啟動要等」開始是使用者
   感覺得到的事，而線性外推本身也該被實測取代）。
2. 啟動路徑加入其他也要掃全語料的工作，使雜湊不再是可忽略的一項。
3. 續讀檢查從「每次啟動」變成「更頻繁」（例如檔案監看觸發）。

## 誠實邊界

- 這是**單機、單次**量測，沒有跑多次取分佈，也沒有在冷檔案快取下重跑。1,373 MB/s
  這個數字在檔案已被 page cache 涵蓋時會偏高——所以它是**樂觀**的一側。要用它推
  「一定夠快」之前，該補一次冷快取量測。
- 它不涵蓋這條路徑的其餘部分，所以**不能**讀成「`ltm build` 的增量掃描要 4 秒」。

## 補記（2026-09-01，#56）

重議發生了，但**不是因為上面三個觸發的任何一個**：語料 5.42 GB（未達 20 GB）、
啟動路徑沒有新增全掃工作、頻率也沒變。實際命中的是清單沒列到的第四種情況：
**這條路徑成為互動查詢延遲的主導項**（92%，見
[`2026-09-01-scan-parallelism.md`](2026-09-01-scan-parallelism.md)）——上面那份
封閉列舉漏了「佔比」這個軸。

處置也不是本檔比較過的 Merkle，而是第三個選項：**逐檔並行**（正交於 Merkle：
Merkle 降低單次改動的工作量，並行縮短同量工作的牆鐘）。「每 byte 都被核對」的
性質保留，本檔的結論（不換 Merkle）不變；若並行後仍要再壓，Merkle 是下一個
候選，屆時以新紀錄重議。
