# `ltm query` 的延遲分解（#48 之後、ANN 重議、SessionEnd hook 三者共用）

**日期**：2026-08-27
**機器**：MacBook Pro M5 Max（18 核、128 GB）
**binary**：`.build/release/ltm`，commit `666c332`
**索引**：當天首次成功的全量 build——640,760 chunk、`vectors.bin` 1.3 GB、
`index.sqlite3` 1.8 GB、語料 9,958 檔／5.67 GB

## 為什麼量這個

`docs/measurements/2026-08-08-baseline.md` 說「暴力 cosine 是毫秒級、不需要 ANN，
等超過幾百萬 chunk 再議」，而那是在 **280,000 chunk 的估計**上做的判斷。實際建出來
是 **640,760**，估計低了 2.29 倍，所以那個結論的前提要重新檢查。

同時 `.claude/rules/ltm-analogy.md` 明寫：要重開「SessionEnd hook 預先併入」的討論，
必須先有一份「查詢前的增量併入耗時」紀錄。本檔就是那一份。

## 方法：四點差分

每個條件連跑 3–5 次取 min/median/max。各條件之間只差一段工作：

| 條件 | 包含 | median |
|---|---|---|
| C. `ltm query --help` | 純行程啟動 | **0.01 s** |
| D. 空語料 `ltm build --quiet` | ＋開索引（＋可能的模型載入，見誠實邊界）| **0.08 s** |
| A. `ltm build --quiet`（索引已最新）| ＋掃 9,958 檔／5.67 GB 的增量併入 | **6.58 s**（min 6.11）|
| B. `ltm query <字串> --all-projects` | ＋查詢字串 embedding ＋讀 1.3 GB 側車 ＋ FTS ＋暴力 cosine | **6.19 s**（min 6.12）|

### 誠實邊界（本節被上表的 D 列引用；先前它不存在）

四點差分的每一條歸屬都建立在「相鄰兩個條件之間只差一段工作」上，而這一點有兩處
**不完全成立**，必須寫在這裡而不是預設讀者會想到：

1. **D 不是乾淨的「開索引」。** 它是對**空語料**跑 `build --quiet`，所以它含了
   行程啟動、開 DB，**可能還含模型載入**（embedder 在沒有 chunk 要算時是否載入，
   本檔沒有查證）。若含，`A − D` 會**低估**掃描；若不含，`A − D` 裡混進了模型載入。
   兩個方向都沒有排除。
2. **A 與 B 的語料狀態不同。** A 跑在「索引已最新」的前提上（掃完沒有新內容），
   B 是一次真實查詢。兩者之間除了查詢本身，還差「A 那一輪剛剛把 page cache 烘熱」。

所以 `A − D ≈ 6.5 s「全部是掃描」`是一個**近似**，不是被控制組證立的等式
（#49 R2 verify，codex lens）。要把它變成等式，需要的是 in-process 計時，本檔沒做。

## 結果一：向量檢索不是瓶頸

**B − A 落在雜訊以下。** A 自己的執行間變異是 6.11–8.23 s，而 B 的中位數比 A 的
中位數還低。也就是說「讀 1.3 GB 側車 ＋ 對 640,760 個 512 維向量算暴力 cosine ＋
FTS 查詢」這一整段，在這個量測的解析度下**量不出來**。

**這回答了「現在要不要上 ANN」，答案是不要**：在這個規模、這台機器、這個使用形態
下，被優化的對象根本不在這裡。baseline 的重議門檻（`:72`「chunk 數逼近百萬」）
問錯了維度——它問 chunk 數，而決定成本的是掃描。

**但它不支持「答案與規模無關」，也不支持「chunk 再翻一倍仍然不是主要成本」。**
本檔只有**一個規模點**（640,760 chunk），而從一個點推不出任何斜率——先前這裡
寫的正是那句外推（#49 R2 verify，codex lens）。可以說的是：向量那一段目前小到
量不出來，所以要判斷它何時會變成瓶頸，需要的是**第二個規模點**，不是這一份紀錄。

**這份紀錄不支持**「暴力 cosine 是 X 毫秒」這種陳述。它只支持「它相對於 6 秒小到
量不出來」。要那個數字得做 in-process 計時，本檔沒做。

## 修正後（#49 修完，commit `8376be7`）

`CorpusScanner` 對每個來源檔把已處理前綴**讀取並 SHA-256 兩次**——續讀比對一次、
寫回 state 再一次。沒有新內容時第二次的輸入與輸出都與第一次相同。移除之後（同一台
機器、同一份語料、同一天，各 7 次）：

| 條件 | 改前 med | **改後 med** | 差 |
|---|---|---|---|
| A. `build --quiet`（索引已最新）| 6.58 s | **3.56 s**（min 3.33 / max 3.98）| **−3.02** |
| B. `query` | 6.19 s | **3.79 s**（min 3.70 / max 3.98）| **−2.40** |

### `2.27` 與 `4.51` 是**模型值**，不是量測

先前這一段（以及 `CorpusScanner` 的出貨註解）把 `2.27` / `4.51` 稱為「實測」，
並拿它們去對帳。**它們不是。** 診斷階段唯一實際量到的是下面「結果二」那一列——
Python + OpenSSL 對整份語料做**一次**全讀 + SHA-256 的 **2.39 s**；`2.27` 是從它
推出來的模型，`4.51` 是那個模型 ×2。用一個模型去對帳另一組實測，落差沒有意義。
（#49 R2 verify，devil's advocate。）

**改用實測差來歸屬**——本次改動移除的正好是兩次讀+雜湊當中的一次，所以那一次的
代價**被直接量到了**：

| 條件 | 改前 − 改後 | 這個差代表什麼 |
|---|---|---|
| A. `build --quiet` | **−3.02 s** | 被移除的那一次讀+雜湊，在真實程式路徑上的代價 |
| B. `query` | −2.40 s | 同上，但含查詢自身的變異（B 的 min/max 區間與這個差同量級）|

以 A 的差為準：

```
A_pre  − D ≈ 6.50 s   ＝ 兩次讀+雜湊 ＋ 其餘
A_post − D ≈ 3.48 s   ＝ 一次讀+雜湊 ＋ 其餘
差             3.02 s   ＝ 被移除的那一次（實測）
```

**剩下 3.48 s 裡有多少是必要的那一次，本檔答不出一個精確值。** 上界是 3.48 s
（全部都是它）。**下界本檔給不出來。**

先前這裡寫「一個合理的下界是 2.39 s（隔離量到的單次全讀+雜湊）」並據此推出
「未歸屬 0–1.1 s」。**那是把一個模型值換成另一個模型值。** 那個 2.39 s 是
**Python + OpenSSL** 量的，而保留下來的那一次是 **Swift + CryptoKit**，跑在不同
的 page-cache 狀態下——跨 executable、跨 hash 實作的下界關係沒有任何量測支撐，
而本檔上一節才剛承認 `A − D` 自己混有 confound。（#49 R3 verify，codex + logic。）

所以能說的只有：**未歸屬 ≤ 3.48 s**，上界，沒有下界。要收窄它需要 in-process
計時，本檔沒做。

兩次的代價不必相等（第二次讀的是第一次剛烘熱的 page cache，理應更便宜），所以
「移除的那次要 3.02 s ⇒ 留下的那次也要 3.02 s」**不成立**，本檔不這樣推。

**離群值要記**：第一輪量測（各 3 次）出現一個 **55.87 s** 的 A 值。之後 7 次重量
全部落在 3.33–3.98，未能重現。可能是 release build 剛結束的冷 cache、或與同時在跑的
`ltm mcp` 行程競爭——**兩者都沒有查證**。記在這裡是因為它真的發生過，不是因為知道
它是什麼。

**這不是「解決了 6 秒問題」。** 移除的是可證明冗餘的那一半（實測 −3.02 s）；
剩下的 3.48 s 大部分是**必要的**續讀比對（省不掉，只能換機制，而那被本 repo 目前
不存在的延遲目標值擋住），其餘未歸屬。

**「3.79 s 仍然不是互動級延遲」這句先前寫在這裡，本檔收回它。** 本 repo 沒有延遲
目標值，所以「夠不夠快」在這裡沒有判準——一個沒有判準的效果分類就是一個宣稱
（#49 R2 verify，codex lens）。能說的只有那個數字本身。

## 結果二：6 秒幾乎全在掃描

A − D ≈ **6.5 秒**，**近似**等於「掃 9,958 檔的增量併入」。

「近似」不是客套：本檔的〈誠實邊界〉列了兩個 confound（D 可能含模型載入、
A 與 B 的 page-cache 狀態不同），而它們都沒有被排除。先前這一行寫的是無條件的
「全部是」——**同一份紀錄對同一個數字有兩套不相容的歸因**，正是 R2 抓到、
本輪宣稱修掉的那個缺陷，只是換了位置（#49 R3 verify，codex）。

已歸屬的部分：續讀檢查會把每個檔案的已處理前綴**整段重讀並算 SHA-256**
（`CorpusScanner` 的 `prefixHash`）。當天實測：

| | |
|---|---|
| 檔數 | 9,958 |
| 位元組 | 5,665,527,427（5.67 GB）|
| 全讀 + SHA-256 | **2.39 秒** |
| 吞吐 | 2,371 MB/s |

查法（可重跑）：

```bash
python3 -c "
import hashlib,time,pathlib
fs=list((pathlib.Path.home()/'.claude/projects').rglob('*.jsonl'))
t=time.time(); n=0
for f in fs:
    with open(f,'rb') as fh:
        h=hashlib.sha256()
        while (b:=fh.read(1<<20)): h.update(b); n+=len(b)
print(len(fs), n, time.time()-t)"
```

**先前這裡寫「2.39 / 6.5 ≈ 39% 有歸屬，剩下約 4 秒沒有歸屬」——那個算式是錯的**
（#49 R2 verify，codex lens：同一份 6.5 秒在本檔有兩套不相容的分解）。分子是
**一次**讀+雜湊，分母涵蓋的程式碼**跑了兩次**。分子與分母不是同一件事。

改用上一節那個實測差來算：被移除的那一次實測 3.02 s，所以兩次至少佔
6.5 秒裡的一半以上。**未歸屬的量請看上一節那個 0–1.1 s 的區間，不是這裡曾經寫過
的 4 秒。** 剩餘部分的候選（未隔離量測，不得當成結論）：目錄走訪與 `stat`、
尾段 JSON 解析、`ScanState` 的 9,935 筆讀寫、SQLite 的 `chunk_sources` 查詢。
**哪一項佔多少，本檔答不出來。**

`2026-08-26-resume-prefix-hash-cost.md` 量到的是 3.96 s／1,373 MB/s，本檔是
2.39 s／2,371 MB/s。差異方向與 page cache 一致（本檔在全量 build 剛結束時量，
cache 是熱的），但**沒有做冷／熱對照**，所以那個歸因也是推測。實際的續讀成本
應落在兩者之間，視 cache 狀態而定。

## 這份紀錄改變了什麼

`2026-08-26-resume-prefix-hash-cost.md` 的結論是「現在不換 Merkle，上界才 4 秒」。
那個判斷把它當成**啟動成本**在評估。本檔指出它是**每次查詢**都要付的——`LTMService`
在每次 `query()` 前跑 `refreshIncrementally()`，而 MCP server 是常駐行程，所以
行程啟動與模型載入被攤掉了，**掃描沒有**。

「4 秒的一次性啟動成本」與「每次記憶查詢固定 4 秒」是兩個不同的決定問題，而先前
只評估過前者。那份紀錄自己寫明了 Merkle 買的是「成本隨改動量而非總量成長」——
那正是這個使用形態需要的東西。

## 不支持的結論

- 任何「暴力 cosine 是 X 毫秒」的數字。
- 「那 6 秒**全部**是 SHA-256 造成的」——未歸屬的量見上，本檔只給得出**上界**。
- 「未歸屬只有 1 秒出頭」——那個下界需要跨 executable 的比較，本檔沒做。
- 「換 Merkle 會讓查詢快 N 倍」——未歸屬的那一段可能不受 Merkle 影響。
- 冷 cache 下的任何數字。本檔全部在熱 cache 下量。
- **任何關於規模的斜率。** 只有一個規模點。
- **任何「夠快／不夠快」的分類。** 本 repo 沒有延遲目標值。
- `2.27` / `4.51` 這兩個數字作為量測——它們是模型值，見上。
