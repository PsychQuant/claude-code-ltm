# 延遲預算

「這次改動夠不夠快」要有一個可以指名的比較對象。這份文件就是那個對象：recall hook 與 MCP `ltm_query` 各一個端到端預算（從送出到拿到答案），CLI 不設。預算由使用者拍板（#76）。

## 這份文件是什麼、不是什麼

**預算是偏好，不是量測。** 它回答「願意為了回想多等多久」，那是偏好，沒有任何實測能替代。所以：

- 它**可以**當門檻：拿一份量測紀錄量到的端到端耗時跟它比，判斷「夠不夠」。
- 它**不可以**當效果宣稱的依據。「改完之後在預算內」仍然是一個效能宣稱，照 `CLAUDE.md` 的誠實邊界，必須有一份 `docs/measurements/` 底下涵蓋那個比較的紀錄。這份文件只提供比較的另一端。

硬上限與預算要分開讀。硬上限是「超過就壞」的線（hook 被取消、MCP 呼叫被中止）；預算是「超過就算慢」的線。hook 的 28 秒逾時不代表 28 秒以內都可以。

## 怎麼拿它比

預算比的是**某個入口的端到端耗時**，所以只有在那個入口上量到的端到端數字能拿來比。只量了某一段成本的紀錄（例如 build 路徑上的一個固定項）不能直接拿來比，也不能從「這段省了多少」推算「改完之後會不會落在預算內」——那是沒有量測支撐的預測。要說「夠不夠」，就要在入口上量一次端到端耗時。

- **#73、#75**：量的是 build 路徑上的成本，不是表上的入口。它們的結論若要說到「夠不夠」，需要另外量入口的端到端耗時；只說「這段成本是多少」則不需要這份文件。
- **#71**：MCP 查詢前併入的預設上限從 30 秒導出。上限要扣掉檢索本身的時間，而且如表中所寫，它不是端到端上界；怎麼分配在 #71 決定。今天的索引規模上檢索本身要多久沒有量過；640,760 個 chunk 時的拆解見 `docs/measurements/2026-08-27-query-latency-decomposition.md`。
- **#79**：hook 的現行設定比預算長，先量再決定要不要改。

## 與 #56「1 秒以內」的關係

#56 的「1 秒以內」是工程目標，沒有說誰在等、在哪個情境下等。判斷「夠不夠」一律以這份文件為準；那個 1 秒不是預算。

## 什麼時候要改這份文件

預算是現在的偏好；語料與使用方式改變後，偏好也可能改變。改的時候在 issue 上留一則 Decision，表格中那一列的「決定」欄寫新的日期與出處（只改一列時其他列不動），舊的值不必保留在這裡，git 歷史有。
