# 延遲預算

「這次改動夠不夠快」要有一個可以指名的比較對象。這份文件就是那個對象：每個入口一個端到端預算（從送出到拿到答案），由使用者拍板（#76）。

## 預算

| 入口 | 誰在等 | 硬上限（超過就壞） | 預算（超過就算慢） | 現行設定 | 落差 |
|---|---|---|---|---|---|
| recall hook（`UserPromptSubmit`） | 使用者：prompt 送出後，hook 跑完才進模型 | `plugin/hooks/hooks.json` 宣告 28 秒；超過時 Claude Code 丟棄這次 hook | **5 秒** | `GUARD` 預設 20 秒（`LTM_RECALL_GUARD_SECONDS`，上限 25 秒）；查詢前併入預算 `GUARD − 5` | 現行比預算長。要不要改預設值，先量再決定：#79 |
| MCP `ltm_query` | agent：工具呼叫回來之前，那一輪停著 | 120 秒後 client 把呼叫移到背景；1800 秒沒有回應或 progress 就中止 | **30 秒** | 查詢前併入沒有上限 | #71 以這個預算導出預設上限 |
| CLI `ltm query` | 在終端機打指令的人 | 無 | 不設 | 預設無上限；`--max-refresh-seconds N` 可自行限制 | — |

決定：2026-10-11，使用者（#76，`issuecomment-6106345492`）。

## 這份文件是什麼、不是什麼

**預算是偏好，不是量測。** 它回答「願意為了回想多等多久」，那是偏好，沒有任何實測能替代。所以：

- 它**可以**當門檻：拿一份量測紀錄量到的端到端耗時跟它比，判斷「夠不夠」。
- 它**不可以**當效果宣稱的依據。「改完之後在預算內」仍然是一個效能宣稱，照 `CLAUDE.md` 的誠實邊界，必須有一份 `docs/measurements/` 底下涵蓋那個比較的紀錄。這份文件只提供比較的另一端。

硬上限與預算要分開讀。硬上限是「超過就壞」的線（hook 被丟棄、MCP 呼叫被中止）；預算是「超過就算慢」的線。30 秒的逾時不代表 30 秒以內都可以。

## 誰在用它

- **#73**：`chunkCount()` 值不值得改，看它在端到端耗時裡佔多少、拿掉之後會不會讓某個入口從超過預算變成不超過。
- **#75**：#61 的前後量測，拿兩邊的端到端耗時對照這裡的預算。
- **#71**：MCP 查詢前併入的預設上限從 30 秒導出。上限要扣掉檢索本身的時間，而檢索本身要多久還沒有量過，所以怎麼分配在 #71 決定，不在這裡。
- **#79**：hook 的現行設定超過預算，先量再改。

## 什麼時候要改這份文件

預算是現在的偏好；語料與使用方式改變後，偏好也可能改變。改的時候在 issue 上留一則 Decision，表格的決定欄寫新的日期與出處，舊的值不必保留在這裡（git 歷史有）。
