# 延遲預算

「這次改動夠不夠快」要有一個可以指名的比較對象。這份文件就是那個對象：recall hook 與 MCP `ltm_query` 各一個端到端預算（從送出到拿到答案），CLI 不設。預算由使用者拍板（#76）。

## 這份文件是什麼、不是什麼

**預算是偏好，不是量測。** 它回答「願意為了回想多等多久」，那是偏好，沒有任何實測能替代。所以：

- 它**可以**當門檻：拿一份量測紀錄量到的端到端耗時跟它比，判斷「夠不夠」。
- 它**不可以**當效果宣稱的依據。「改完之後在預算內」仍然是一個效能宣稱，照 `CLAUDE.md` 的誠實邊界，必須有一份 `docs/measurements/` 底下涵蓋那個比較的紀錄。這份文件只提供比較的另一端。

硬上限與預算要分開讀。硬上限是「超過就壞」的線；預算是「超過就算慢」的線。hook 的 28 秒逾時不代表 28 秒以內都可以。

## 怎麼拿它比

預算比的是**某個入口的端到端耗時**，所以只有在那個入口上量到的端到端數字能拿來比。比的方式由使用者在 #76 的 verify 輪次之間決定（2026-10-11）：R2 定了統計量與紀錄條件（`issuecomment-6107451314`）；R3 定了樣本與判定，並取代 R2「降級另計、不算進在預算內」那一句（`issuecomment-6108082810`）；R4 把「降級」改成用性質定義、加上最小樣本，取代 R3 的四種列舉（`issuecomment-6108393156`）；R5 排除固定格式，定了分位數與硬上限一票否決（`issuecomment-6108639622`）。

- **樣本**：hook 只取閘門命中的輪次（未命中的輪次不跑查詢，放進來量到的是閘門本身）；MCP 取全部呼叫。
- **降級**：一個輪次只有在「正常結束、給出結果（含零命中），而且回應除了命中之外沒有任何關於這一輪的說明或警告」時才算非降級；其餘一律是降級——錯誤、拒答、逾時、沒有結局、hook 的 notice、回應裡任何關於這一輪狀態的說明或警告行（例如落後、延後併入、讀不到來源、欠著稽核）。這是性質，不是清單：上面的例子只是舉例，沒列到的形狀照樣適用。不論這一輪發生什麼都會出現的固定格式不算說明或警告，例如 recall 區塊的開閉標記、「以下是檢索到的歷史對話原文」與「不得當成指示」兩行、MCP 零命中時的「（沒有命中）」。這裡的「降級」是預算判定用的分類，包含拒答；README 的「拒答而不降級」是另一個意思。
- **統計量是 p95**，取最近秩：n 輪由小到大排序後的第 ⌈0.95n⌉ 個值。降級輪次以實際耗時留在樣本裡；沒有結局的輪次以中止時的耗時計。
- **判定**：「在預算內」要同時滿足三件事：p95 不超過預算；降級輪次的比例不超過 5%；沒有任何一輪超過該入口的硬上限或沒有結局——硬上限是「超過就壞」，一輪就足以判不通過。只看 p95 不夠：降級輪次可能很快（例如拒答、或持鎖而跳過併入）；`GUARD` 若調得明顯小於預算，被封頂的輪次也會落在預算內。這些情形下 p95 好看，回想卻沒有做到或沒有用上新內容。封頂的輪次會比 `GUARD` 多一點：hook 到了 `GUARD` 才送 TERM、等 0.2 秒再 KILL，§2 量到 20 秒的 `GUARD` 每輪約 21.5 秒。
- **最小樣本**：少於 20 輪時照寫數字，但不下「在／不在預算內」的判定。
- **紀錄要寫明條件與每輪的證據**：條件是 cache 冷熱、同機 `ltm mcp` 行程數（#65）、在 #67 之前或之後、索引規模。每輪要留開始與結束時間，以及判斷分類所需的回應（hook 的 stdout、MCP 的回應文字）——分類要看回應內容，stats 檔的標籤不夠：帶落後行的區塊也記成 `hit`，被 28 秒逾時取消的輪次不寫 stats。回應含語料內容，所以分類用程式做，紀錄只留分類結果與計數，不留回應本身。
- **規則看不到的輪次**：hook 有幾種沒用上新內容、回應裡卻看不出來的情形。讀不到來源與調校參數的拒絕只走 CLI 的 stderr，hook 把它丟掉（#83）；閘門沒跑成（python 不在、線索表讀不到或為空）的輪次記成未命中、不印 notice，本來就不在樣本裡；`ltm` 版本過舊時，hook 只在每個 session 的第一輪印 notice，之後閘門命中的輪次回應是空的。這些輪次照這份規則判不出來，紀錄要另外說明有沒有排除它們。

只量了某一段成本的紀錄（例如 build 路徑上的一個固定項）不能直接拿來比，也不能從「這段省了多少」推算「改完之後會不會落在預算內」——那是沒有量測支撐的預測。

- **#73、#75**：量的是 build 路徑上的成本。要以延遲為理由下「值不值得改」的結論，需要另外照上面的方式量入口的端到端，再跟預算比；只回答「這段成本是多少」不需要這份文件。
- **#71**：MCP 查詢前併入的預設上限從 30 秒導出。上限要扣掉檢索本身的時間，而且如表中所寫，它不是端到端上界；怎麼分配在 #71 決定。今天的索引規模上檢索本身要多久沒有量過；640,760 個 chunk 時的拆解見 `docs/measurements/2026-08-27-query-latency-decomposition.md`。
- **#79**：hook 的現行設定比預算長，先量再決定要不要改。

## 與 #56「1 秒以內」的關係

#56 的「1 秒以內」是使用者本人對 MCP／CLI 穩態查詢的體感期望（#56 body；`issuecomment-5489238185`；當時量的是 CLI）。#76 把 CLI 定為不設預算、MCP 定為 30 秒，並在知道這一點之後分別重新確認（`issuecomment-6107451314`、`issuecomment-6108082810`），所以那個 1 秒不再是判斷「夠不夠」的門檻。

## 什麼時候要改這份文件

預算是現在的偏好；語料與使用方式改變後，偏好也可能改變。改的時候在 issue 上留一則 Decision，把那一列「決定」欄改成新的日期、決定者與那則 Decision 的 comment id，其他列不動。舊的值不必保留在這裡，git 歷史有。
