# 記憶系統：可比較的策略空間

本專案刻意**不選定**單一記憶模型。不同策略在同一份語料、同一組查詢上跑，可以比較——
這一頁定義比較的框架，各策略的細節另立檔案。

## 為什麼保留這個軸

設計過程中出現過一次關鍵反轉，值得記錄，因為它會一再出現：

初版設計把「提取次數影響排序」列為三大風險（富者愈富、popularity bias、可重現性斷裂），
主張用 ±5% 封頂把它壓到幾乎無效。反駁是一句話：

> 你的批評其實剛好是人類記憶系統的缺點吧

這是對的。提取練習效應（retrieval practice）、可得性捷思（availability heuristic）、
重建式記憶（Bartlett）——**被列為缺陷的三件事，正是人類記憶的真實特徵**。把它們消掉
不是「修正錯誤」，是**選擇了另一種記憶模型**（檔案櫃），而那個選擇被偷渡成了預設值。

所以策略不該寫死在架構裡。**它是參數，不是前提。**

## 比較的三個軸

| 軸 | 問題 | 極端 A | 極端 B |
|---|---|---|---|
| **保真** | 回傳的是原文還是改寫？ | 逐字原文 | LLM 摘要 |
| **可重現** | 同一 query 兩週後結果一樣嗎？ | 完全確定 | 受使用歷史調變 |
| **關聯** | 命中會不會擴散到相鄰記憶？ | 只回命中 | 擴散激發 |

三軸互相牽制：關聯擴散提高召回但傷可重現；LLM 摘要提高可讀性但傷保真。
**沒有全贏的點**，所以要能量測、能切換。

## 候選策略

各策略共用同一個檢索底座（BM25 + 向量 RRF），差別在記憶層怎麼介入。

| 策略 | 記憶層行為 | 像什麼 | 狀態 |
|---|---|---|---|
| `archival` | 無。純內容相關性排序 | 檔案櫃／grep | 已實作（`LTMQuery`）|
| `conservative` | 只在 base score 完全相等時以強度決勝 | 加了書籤的檔案櫃 | 已實作（`LTMQuery`）|
| `human-like` | power-law decay + 提取增強，帶內重排、提升有上限 | 人腦 | **部分實作**（`LTMQuery`）|

> **`human-like` 缺一個機制，這裡明說。** issue 要的第三個機制是 **spreading
> activation**（Collins & Loftus, 1975；issue 裡叫「共現擴散激發」，Clarity Surface
> 已裁決共現實作只是它的一個變體）——**目前沒有實作**。它需要一個共現邊結構，
> 而事件 schema 還沒帶那個東西；補上去會讓這次改動超出「定義 seam」的範圍。
> 列為 follow-up。
>
> 這條記在這裡，是因為先前的 `proposal.md` 把 "co-retrieval association" 列進
> 已 ship 的機制、本表也標成「已實作」——那是過度宣稱，由 #1 的 verify
> （2026-08-11）抓出並更正。**部分實作就寫部分實作。**

### `conservative` 一度被移除，又被改回來——這段值得記

初版實作把 `conservative`（「strength 只當 tie-breaker，影響封頂 ±5%」）**整檔移除**，
論證是「那條規則無法表達」：RRF 分數是 rank 導出的、與查詢相對，同一個數值差在不同
查詢裡意義不同，輸入清單深度一變分數分佈就跟著移動，所以「±5%」沒有穩定的指涉對象。

**那個論證只對了一半。** ±5% 確實無法表達，但「**僅作 tie-breaker**」在這套詞彙裡
完全可以表達——就是「同帶內 base score 完全相等時以強度決勝」。#1 的 verify 兩個 lens
各自指出這點：**部分為真的論證被用來支撐全稱結論**，而那正是本專案要防的錯誤類型。

所以它被改回來了。三檔的差別現在是**機制**，不是幅度：

| 策略 | 何時作用 |
|---|---|
| `archival` | 從不 |
| `conservative` | 只在檢索沒有意見時（base score 完全相等）|
| `human-like` | 只要歷史有差就作用，受提升上限約束 |

`conservative` 與 `human-like` **吃同一組訊號**，差在條件。這不違反「策略由訊號集合
定義、不由幅度定義」——把 `human-like` 的上限調到 0 得不到 tie-breaking，只得到
「什麼都不做」，兩者是不同機制而非不同強度。code 裡有一條測試直接釘住這件事。

### 位移上限：對稱 → 單向 → 又改回對稱

上限**對稱**：提升與下移都不得超過 `bound`。這條改過兩次，兩次都留在這裡，因為
中間那一步錯了，而它在當下看起來有充分理由。

初版契約是對稱的，演算法卻只約束提升，於是 verify R1 抓到**內建策略對一般輸入
拋錯**。R1 的修法是讓演算法遷就契約：swap 前檢查被越過方的累計下移，超限就放棄
提升。那讓它合規了，但引入**楔住**——帶首的擋路者用完預算後，上方位置對後續
候選永久封死。

R2 量到「帶大小 32、31 個有歷史 → 只有 1 次提升」，判定 human-like 幾乎被關掉。
**我當時改了契約**（改成只約束提升），論證是「對稱上限的算術必然讓整帶提升總數
≤ bound」。

R3 指出那句話**是錯的**：bound 1、`[A,B,C,D] → [B,A,D,C]`，每筆位移都 ≤1 卻有
兩個提升。被量測推翻的是 R1 的**演算法**，不是契約。而且 R2 那個輸入的第 0 名
以外本來就已按強度排好——目標順序只差「把第 0 名移到最後」，**1 次提升是最佳解，
不是飢餓**。量測為真、詮釋有誤，而我照著錯的詮釋改了契約。

所以：契約改回對稱，換掉演算法。現在是 pass-based——每個元素每輪最多參與一次
交換，跑 `bound` 輪，兩個方向的上限由構造保證，且沒有「放棄提升」規則所以不楔住。

預設值仍是 1 且仍標 **provisional**。**不要為了讓效果看起來明顯而調高它**：
那會讓比較實驗量到的是參數，不是策略。

**這段留著的理由**：「改掉自己 code 一直違反的規則」在當下有充分理由，而它錯了。
只寫結論的話，下一個人會再走一次。

### 比較方式是 interleaving，不是重放歷史查詢

重放歷史查詢是標準做法，也方便得多——但它需要留著 query 原文，而 query 經常含第三方
姓名與未發表內容，記憶層的硬約束把它擋在外面。**不留 query 是隱私決定，比較方式改用
interleaving 是這個決定的直接後果，不是疏忽。**

做法：同一次查詢由兩個策略各出排序，交錯成一份清單呈現，看使用者點開哪一邊
（team-draft）。只需要已經同意記錄的事件（`shown` / `opened` / `cited`）。代價是**回溯式
比較不可能**——只能比較「現在這兩個策略」，不能拿舊資料重跑一個新策略。

兩個伴隨的紀律：

- **報告一律分桶，不得只給整體數字。** #2 的實測顯示向量融合的整體 +1pp 增益 100% 集中
  在中文雙字桶；只看整體會判成「沒有差異」。分桶用的是一個封閉五值的 query class label
  （`cjk-2char` / `cjk-3char` / `cjk-4plus` / `latin-alnum` / `mixed`），它從 query 算出後
  query 即丟棄——label 是統計不是內容，所以它可以留，原文不行。
- **兩邊排序相同時不記給任何一方**（null comparison）。硬記會憑空製造偏好。

預期結果值得先講明：`archival` 與 `human-like` 在**整體**上很可能統計不可分辨。這不是
實作失敗，是效果量本來就可能小於雜訊——所以逐桶那幾列才是要看的東西。

## 待決問題

- 評估集怎麼累積才不會只反映「我已經知道去哪找」的查詢（選擇偏誤）
- 策略切換的粒度：全域設定？per-query flag？兩者都要？
- `human-like` 的參數（decay k、boost 幅度、擴散深度）是沿用 AI4o 的值，還是在
  這份語料上重新校準？語料性質差很多（技術對話 vs 日常聊天）
