# 記憶系統：可比較的策略空間

本專案刻意**不選定**單一記憶模型。不同策略在同一份語料、同一組查詢上跑，可以比較——
這一頁定義比較的框架，各策略的細節另立檔案。

## 為什麼保留這個軸

設計過程中出現過一次關鍵反轉，值得記錄，因為它會一再出現：

初版設計把「提取次數影響排序」列為三大風險（富者愈富、popularity bias、可重現性斷裂），
主張用 ±5% 封頂把它壓到幾乎無效。反駁是一句話：

> 你的批評其實剛好是人類記憶系統的缺點吧

這是對的。提取練習效應（retrieval practice）、可得性捷思（availability heuristic）、
重建式記憶（Bartlett）——**被列為缺陷的三件事，正是人類記憶的真實特徵**。把它們消掉
不是「修正錯誤」，是**選擇了另一種記憶模型**（檔案櫃），而那個選擇被偷渡成了預設值。

所以策略不該寫死在架構裡。**它是參數，不是前提。**

## 比較的三個軸

| 軸 | 問題 | 極端 A | 極端 B |
|---|---|---|---|
| **保真** | 回傳的是原文還是改寫？ | 逐字原文 | LLM 摘要 |
| **可重現** | 同一 query 兩週後結果一樣嗎？ | 完全確定 | 受使用歷史調變 |
| **關聯** | 命中會不會擴散到相鄰記憶？ | 只回命中 | 擴散激發 |

三軸互相牽制：關聯擴散提高召回但傷可重現；LLM 摘要提高可讀性但傷保真。
**沒有全贏的點**，所以要能量測、能切換。

## 候選策略

各策略共用同一個檢索底座（BM25 + 向量 RRF），差別在記憶層怎麼介入。

| 策略 | 記憶層行為 | 像什麼 | 狀態 |
|---|---|---|---|
| `archival` | 無。純內容相關性排序 | 檔案櫃／grep | 已實作（`LTMQuery`）|
| `conservative` | 只在 base score 完全相等時以強度決勝 | 加了書籤的檔案櫃 | 已實作（`LTMQuery`）|
| `human-like` | power-law decay + 提取增強，帶內重排、位移有上限 | 人腦 | **部分實作**（`LTMQuery`）|

`human-like` 的公式沿用 `PsychQuant/ai4o` 的 `docs/memory/implementation/`
（`memory-strength.md` / `consolidation.md`），那套已按 Wixted & Ebbesen (1991) 的
power-law 調過，不重推。**參數是否適用於本語料未經校準**——AI4o 的值是在日常聊天
語料上調的，claude-LTM 是技術對話，性質差很多。

**一處刻意的偏離**：AI4o 會把低 strength 記憶 `archived = true` 排除於候選之外，
理由是省 recall window 的 token。claude-LTM 是全庫檢索、沒有 window 壓力，照抄
archive 會讓正回饋**把記憶永久埋掉**。因此 `human-like` 的低 strength 只回到中性
（boost = 1.0），永遠留在候選集。

> **`human-like` 缺一個機制，這裡明說。** issue 要的第三個機制是 **spreading
> activation**（Collins & Loftus, 1975；issue 裡叫「共現擴散激發」，Clarity Surface
> 已裁決共現實作只是它的一個變體）——**目前沒有實作**。它需要一個共現邊結構，
> 而事件 schema 還沒帶那個東西；補上去會讓這次改動超出「定義 seam」的範圍。
> 列為 follow-up。
>
> 這條記在這裡，是因為先前的 `proposal.md` 把 "co-retrieval association" 列進
> 已 ship 的機制、本表也標成「已實作」——那是過度宣稱，由 #1 的 verify
> （2026-08-11）抓出並更正。**部分實作就寫部分實作。**

### `conservative` 一度被移除，又被改回來——這段值得記

初版實作把 `conservative`（「strength 只當 tie-breaker，影響封頂 ±5%」）**整檔移除**，
論證是「那條規則無法表達」：RRF 分數是 rank 導出的、與查詢相對，同一個數值差在不同
查詢裡意義不同，輸入清單深度一變分數分佈就跟著移動，所以「±5%」沒有穩定的指涉對象。

**那個論證只對了一半。** ±5% 確實無法表達，但「**僅作 tie-breaker**」在這套詞彙裡
完全可以表達——就是「同帶內 base score 完全相等時以強度決勝」。#1 的 verify 兩個 lens
各自指出這點：**部分為真的論證被用來支撐全稱結論**，而那正是本專案要防的錯誤類型。

所以它被改回來了。三檔的差別現在是**機制**，不是幅度：

| 策略 | 何時作用 |
|---|---|
| `archival` | 從不 |
| `conservative` | 只在檢索沒有意見時（base score 完全相等）|
| `human-like` | 只要歷史有差就作用，受提升上限約束 |

`conservative` 與 `human-like` **吃同一組訊號**、而且用**同一個**有界重排核心，差在
餵給它哪些區間。

**這裡的證據挑過兩次，第一次挑錯了。** 原本的論證是「把 `human-like` 的上限調到 0
得不到 tie-breaking」——R4 的 devils-advocate 掃過 bound 0…6 之後指出：那個點的性質
由一句 early return 保證，證不了整個值域；而**在全平手輸入上，bound 夠大時兩者逐字
相同**。也就是說在 `conservative` 唯一會作用的那類輸入上，差別確實只是幅度。

可辯護的證據一直在旁邊：**base score 相異時，沒有任何 bound 能讓 `human-like` 變成
`conservative`**——後者在那裡完全不動，前者只要 bound > 0 就會動。那是條件差異。
兩條事實都寫成了測試，包括 DA 量到的那條收斂——把反例也釘住，下一個人才不會拿
「機制不是幅度」去推導它推不出來的東西。

**`conservative` 不豁免於位移上限。** 它一度豁免（守衛收到一個保證不會觸發的門檻），
那與「策略自己授權自己的上限」是同一個缺陷、只是換個地方寫。tie-run 約束是**額外**
條件不是替代：它在「能否跨越語意區段」更嚴格，在幅度上完全不設限，兩者不可比較。

**這一檔有沒有用仍未量。** off ties 它與 `archival` 的**順序與位移**相同，reason 不同
（`archival` 依契約永不讀 projection，所以它的 history 恆為 none）。所以它的價值完全
等於「精確平手多常發生」。RRF 保證平手**可能**
發生，但**發生率沒量過**（#18）。在量到之前，不得宣稱這一檔「實務上會命中」。

### 位移上限：對稱 → 單向 → 又改回對稱

上限**對稱**：提升與下移都不得超過 `bound`。這條改過兩次，兩次都留在這裡，因為
中間那一步錯了，而它在當下看起來有充分理由。

初版契約是對稱的，演算法卻只約束提升，於是 verify R1 抓到**內建策略對一般輸入
拋錯**。R1 的修法是讓演算法遷就契約：swap 前檢查被越過方的累計下移，超限就放棄
提升。那讓它合規了，但引入**楔住**——帶首的擋路者用完預算後，上方位置對後續
候選永久封死。

R2 量到「帶大小 32、31 個有歷史 → 只有 1 次提升」，判定 human-like 幾乎被關掉。
**我當時改了契約**（改成只約束提升），論證是「對稱上限的算術必然讓整帶提升總數
≤ bound」。

R3 指出那句話**是錯的**：bound 1、`[A,B,C,D] → [B,A,D,C]`，每筆位移都 ≤1 卻有
兩個提升。被量測推翻的是 R1 的**演算法**，不是契約。而且 R2 那個輸入的第 0 名
以外本來就已按強度排好——目標順序只差「把第 0 名移到最後」，**1 次提升是最佳解，
不是飢餓**。量測為真、詮釋有誤，而我照著錯的詮釋改了契約。

所以：契約改回對稱，換掉演算法。現在是 pass-based——每個元素每輪最多參與一次
交換，跑 `bound` 輪，兩個方向的上限由構造保證，且沒有「放棄提升」規則所以不楔住。

預設值仍是 1 且仍標 **provisional**。**不要為了讓效果看起來明顯而調高它**：
那會讓比較實驗量到的是參數，不是策略。

**這段留著的理由**：「改掉自己 code 一直違反的規則」在當下有充分理由，而它錯了。
只寫結論的話，下一個人會再走一次。

### seam 檢查的是「走 `rerank` 的呼叫」，不是所有呼叫

`MemoryStrategy.rerank` 定義在 protocol 的 **extension** 上、不是需求項，所以走這條
路的呼叫必然通過前置條件（base score 有限、帶非遞減、統計形狀）與後置條件（排列性、
帶保持、位移上限、displacement 與 movement 的誠實性）。

**判準：只有經過 `rerank` 這一格的呼叫受約束。** 這句話寫成判準而不是列舉逃逸口，
是因為列舉已經漏過一次——先前這裡寫「擋得住的是經由 seam 的呼叫」並只點名一種例外
（具體型別另外定義同名方法），而 #1 verify R6 在 worktree 外實測到第二種：
`rerankChecked` 是 public requirement，它收的 `ValidatedCandidates` 可儲存、可轉手，
任何合法 conformer 存下 token 之後，模組外就能直接呼叫並跳過全部檢查（實測：回傳 3 筆
／輸入 5 筆，`candidateSetChanged` 沒有觸發）。

所以這一節先前的標題「seam 是型別層事實」是**過度宣稱**，已撤回。要讓它成為型別層
事實，token 必須綁死在單次呼叫上、或 `rerankChecked` 不能是 public requirement——
兩者都是介面重新設計，追蹤於 #14。

**推論，值得單獨記住**：消費端不得因為「seam 保證過了」而省掉自己的檢查。交錯器
就是這樣刪掉自己那道排列檢查的，而它依據的正是上面那句被撤回的話；R6 把它裝回去了。

演進史：前置與後置檢查最初由每個策略**自願**呼叫（R4 修）；位移上限與帶圍籬又晚了
一輪才進 seam（R5 漏、R6 修）；「策略不得謊報自己的 displacement」與 `movement`
分兩輪才補齊（R5 補前者、R6 補後者）。每一次的形狀都相同：**修了兩個欄位裡的一個、
兩條路徑裡的一條。**

### 比較方式是 interleaving，不是重放歷史查詢

重放歷史查詢是標準做法，也方便得多——但它需要留著 query 原文，而 query 經常含第三方
姓名與未發表內容，記憶層的硬約束把它擋在外面。**不留 query 是隱私決定，比較方式改用
interleaving 是這個決定的直接後果，不是疏忽。**

做法：同一次查詢由兩個策略各出排序，交錯成一份清單呈現，看使用者點開哪一邊
（team-draft）。只需要已經同意記錄的事件（`shown` / `opened` / `cited`）。代價是**回溯式
比較不可能**——只能比較「現在這兩個策略」，不能拿舊資料重跑一個新策略。

兩個伴隨的紀律：

- **報告一律分桶，不得只給整體數字。** #2 的檢索基線量測（`docs/measurements/2026-08-08-baseline.md`）
  記錄到向量融合的整體增益集中在中文雙字桶；只看整體會判成「沒有差異」。**那份量測
  比較的是檢索配置，不是記憶策略**——策略之間至今沒有任何量測。分桶用的是一個封閉五值的 query class label
  （`cjk-2char` / `cjk-3char` / `cjk-4plus` / `latin-alnum` / `mixed`），它從 query 算出後
  query 即丟棄——label 是統計不是內容，所以它可以留，原文不行。
- **兩邊排序相同時不記給任何一方**（null comparison）。硬記會憑空製造偏好。歸屬的形狀
  因此**只有兩種**：全部歸屬，或全部不歸屬。混合形狀會讓 per-presentation rate 的分母
  沒有定義，所以它在建構與解碼兩處都被拒絕。
- **起手方是已知的混淆變項，要平衡而且要記下來。** 第 1 個位置的點擊率遠高於其後，
  team-draft 的起手方因此直接影響結果。它一度預設 `.a`（每次呈現都系統性偏向 A），
  改法是拿掉預設值——但那只完成一半：沒給呼叫端平衡機制（最可能的結果是自己寫死
  `.a`），也沒把實際用了哪一邊記進紀錄（於是「偏誤已消除」變成無法驗證的宣稱）。
  現在兩者都有：FNV-1a 的種子分派（**不用 `hashValue`**——Swift 的 `Hasher` 每個
  process 隨機種子化，分派會不可重現），起手方寫進 presentation record。
- **事件的處置恰三種**：計分、合法略過、拒絕。合法略過恰兩種（不屬於任何呈現／
  屬於 null comparison），各自計數並寫進報告——先前它們與拒絕共用同一個 `continue`，
  缺一筆紀錄的後果是分母悄悄變小而報告照常產出。拒絕的**原因**開放擴充，所以
  封閉的是處置這個軸，不是原因清單。

**不預測結果。** 這裡先前寫著「`archival` 與 `human-like` 在整體上很可能統計不可分辨」
——那是一句**方向性的效果量預測**，而本文件下一節的規則明文禁止它。#1 verify R5 抓到
同一份 diff 一邊刪掉那條規則、一邊加進它禁止的宣稱。要說的只有一句：整體數字可能因為
效果量小於雜訊而看不出差異，**也可能不是**，在量到之前兩個方向都沒有根據；逐桶那幾列
是為了讓真有的差異不被整體洗掉，不是因為我已經知道差異在哪裡。

## 評估：沒有 ground truth 就沒有比較

策略可切換只解決一半；另一半是**怎麼知道哪個比較好**。

評估需要一組 `(查詢, 應該命中的 turn 指標)`。這組資料只能從真實回溯情境累積——
每次實際用 claude-LTM 找東西並找到了，就記一筆。**冷啟動時它是空的，這是誠實的
限制，不是可以繞過的細節。**

在有評估集之前，任何「策略 X 比較好」的說法都沒有根據，包括本文件的推薦。

> **這一節在 #1 的實作過程中一度被整段刪掉**（連同上面那句操作性條文），而同一份
> diff 在它原本的位置加進了一句效果量預測。R5 的 codex lens 抓到這件事。留這個註記
> 不是為了自責，是因為它示範了誠實邊界最可能的失效方式：**不是有人反駁它，是它在
> 一次重寫裡安靜地消失，而取代它的文字讀起來很合理。**

### 可插拔的是重排，不是記憶公式

值得明說，因為標題容易讓人以為做到了更多：**這個 change 讓「排序如何被使用歷史影響」
可以換，沒有讓「使用歷史如何被折算成強度」可以換。**

`project()` 在策略被選擇之前就把事件依 power-law 衰減與各類權重彙總成
`reinforcement` / `suppression`，而那個彙總是**有損的**——per-kind 的時間分布之後
拿不回來。交錯器也只能把同一份 projection 同時交給 A 和 B。所以一個「只吃近期
cited、用指數衰減」的策略目前寫不出來，除非同時改 `AnchorStatistics`、`project`、
所有呼叫端與交錯器。

`consumedSignals` 描述的是「重排時看哪些訊號」，**不約束 projection 怎麼算**。

這是介面形狀的限制，不只是實作沒做完（#1 verify R7 的跨模型審查是這樣判的，
而這個判讀被接受）。issue #1 要的是記憶模型不該是寫死的架構前提——排序層做到了，
projection 層沒有。要擴大這個軸，得讓 seam 收保留 kind/timestamp 的策略中立
evidence，或讓一個 policy 同時描述 projection 與重排。列為 follow-up。

## 待決問題

- 評估集怎麼累積才不會只反映「我已經知道去哪找」的查詢（選擇偏誤）
- 策略切換的粒度：全域設定？per-query flag？兩者都要？
- `human-like` 的參數（decay k、boost 幅度、擴散深度）是沿用 AI4o 的值，還是在
  這份語料上重新校準？語料性質差很多（技術對話 vs 日常聊天）
